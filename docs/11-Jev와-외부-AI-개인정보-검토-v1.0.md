# Jev와 외부 AI 개인정보 처리 검토

- 문서 버전: v1.0
- 작성일과 확인 기준일: 2026-10-02
- 최신 개정일: 2026-10-03 — 가입·시작 설정의 법률 검토 질문 보충. 공급자 계약·보안 자료의 확인 기준일은 위 날짜를 유지
- 범위: TypeSafe의 Jev API, 한국 개인정보보호법, GDPR, Gmail 정책, 생성 LLM과 임베딩 API에 전달하는 메일 자료.
- 관련 문서: [웹앱 기획서 v1.6](07-웹앱-기획서-v1.6.md), [에이전트 상세 설계 v0.3](01-에이전트-상세-설계-v0.3.md), [기술 스택 보고서](06-기술-스택-선택-비교-보고서-v1.0.md).
- 확인 방법: 공급자 공식 계약·문서, 국가법령정보센터, 유럽연합 집행위원회, Google 공식 정책을 읽었다. TypeSafe Trust Center는 브라우저의 공개 화면으로 재수탁자 전체 목록과 감사보고서 목록을 확인했다.
- 검토 한계: 우리 명의의 계약·API 계정 설정·운영 시스템·실제 고객 메일은 검사하지 않았다. TypeSafe 감사보고서 원문과 기업용 ZDR 계약은 확보하지 못했다. 공개 설명은 공급자의 진술이며 독립 감사 결과를 직접 검증한 것이 아니다.

운영자가 직접 확인할 일, 조건별 처리 범위, 이용자 동의 체크박스·화면 문안·이용 시나리오는 [개인정보 법률 확인과 사용자 동의 시나리오](13-개인정보-법률-확인과-사용자-동의-시나리오-v1.0.md)에 모았다. 공급자별 공개 조사 결과는 이 보고서에서 유지한다.

## 1. 현재 판단과 기존 결정

**공개 자료만으로 실제 고객 메일을 Jev에 전송할 조건이 충족됐다고 판단할 수 없다.** 재수탁자와 SOC 2 보고서 목록은 추가로 확인했지만, 원문 보관·삭제 기한, ZDR의 적용 범위, 메일 속 제3자 정보의 계약 범위, 개인정보 사고의 책임 등은 서면 확인이 남아 있다.

| 구분 | 현재 상태 |
| --- | --- |
| 사용자 확정 사항 | Luna·Sol 기준 성능 확보 → Jev 결과 미반영 비교 → 중요한 메일 누락이 늘지 않는 검증 범위부터 적용하는 순서는 유지한다. |
| 기존 설계의 제한 | 실제 자료의 비교는 TypeSafe 처리까지 허용된 입력만 사용하며, 허용 조건이 없는 자료는 합성 자료 등으로 대체한다. 결과를 운영에 반영하지 않는 실험도 입력의 외부 전송 조건을 확인한다. |
| 이번 검토의 추천 | 합성 메일 평가를 진행하되, 실제 메일에 대해서는 아래 계약·법적 근거·데이터 흐름·제공사 정책 확인을 먼저 완료한다. 새 운영 정책을 확정한 것은 아니다. |
| 미확인 사항 | 실제 계약 적용, 계정별 ZDR, 감사 범위, 입력별 처리 근거, 우리 시스템의 보안·삭제 구현. 공개 문서 확인과 실제 도입 검증을 구분한다. |

기존 제한의 근거는 [에이전트 상세 설계 9장](01-에이전트-상세-설계-v0.3.md#9-채택한-3단계의-구체적-적용)의 실제 자료 취급 문단이다. 개인정보를 국외로 처리위탁·보관하는 경우도 국외 이전에 포함된다. [개인정보보호법 제28조의8 제1항](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029331979)

## 2. TypeSafe 계약과 공개 보안 자료

확인한 문서의 표기 개정일은 MCA 2026-09-23, DPA 2026-04-24, 개인정보처리방침 2025-11-19다. 실제 계약 검토에는 우리 주문서·수락 기록·적용 버전도 필요하다. [MCA](https://typesafe.ai/legal/mca), [DPA](https://typesafe.ai/legal/data-processing), [개인정보처리방침](https://typesafe.ai/legal/privacy-policy)

| 항목 | 공개 자료에서 확인한 내용 | 추가로 확인할 내용 |
| --- | --- | --- |
| DPA 적용 | MCA 4.4는 DPA 편입을 규정한다. | 우리 계약 주체·호출 경로·주문서에 적용되는 DPA와 변경 계약. 공개 양식의 존재만으로 체결 증빙을 대신하지 않는다. |
| 학습 제한 | MCA 4.1에 사전 동의 없는 고객 데이터 학습 금지가 있다. | 학습 동의 설정, 입력·출력·파생 자료의 범위, 계약 변경 시 통지. |
| Telemetry | MCA 4.1·4.3은 로그·해시·통계·분류 결과 등 활용을 허용한다. | 실제 필드, 본문·식별자 포함 여부, 보유 기간, 익명화와 이용 목적. |
| 보관과 백업 | 구체적인 기본 일수는 제시되지 않고, MCA 10.3에 표준 백업의 보존 예외가 있다. | 입력·출력·오류 로그·캐시·백업별 최대 기간과 삭제 완료 기한. |
| ZDR | 기업 고객용 옵션으로 안내한다. | 계정별 활성화 증빙, 재수탁자·로그·백업·지원 자료의 포함 여부, 예외·가격·최소 약정. |
| 개인정보 처리 지시 | DPA 1.3·2는 개인정보에 대한 목적 제한과 충돌 시 DPA 우선 적용을 규정한다. | Telemetry와 이 제한이 실제 처리에서 어떻게 함께 적용되는지. 광범위한 telemetry 문구만으로 개인정보 무제한 이용을 단정하지 않는다. |
| 정보주체 범위 | DPA Schedule I은 고객과 고객의 이용자를 적고 민감정보 항목을 N/A로 표시한다. | 메일의 발신자·수신자·거래처·직원과 실제 정보 항목을 포괄하는지. 필요한 부속서 보완. |
| 재위탁 | DPA 3은 일반 승인, 새 업체 사전 통지와 15일 내 이의 제기를 규정한다. | 변경 구독 방법, 실제 접근 범위, 이의 미해결 시 전송 중단·종료·삭제 절차. |
| 사고 통지 | DPA 5.2는 인지 후 부당한 지체 없이 최대 72시간 내 통지를 규정한다. | 초기 통지·추가 보고·증거 제공·상시 연락망, 우리 신고와 고객 통지에 필요한 협조. |
| 감독과 감사 | DPA 5.3에 고객 비용으로 12개월당 최대 한 번의 감사와 합의된 범위 등의 조건이 있다. | 사고·규제기관 요청 등 예외와 정기 자료 점검 방법. |
| 배상 한도 | MCA 12는 예외 청구를 제외하고 직전 12개월 요금과 50달러 중 큰 금액을 일반 한도로 정한다. | 개인정보·기밀 유출의 예외 또는 별도 한도, 재수탁자 사고, 보험과 비용 분담. |
| 보안 통제 | 저장 암호화, 암호화 키 접근 제한, 직원 원격 접속의 암호화·MFA, 연간 침투 시험 설명이 있다. | API와 업체 간 전송 암호화, 실제 키 관리·접근 기록·테넌트 격리, 최근 시험의 범위·결과·조치. |
| SOC 2 | 공개 Resources에 SOC 2 Type II - 2026 보고서가 있으며 원문은 접근 신청 대상이다. | 감사 기간·의견·예외, Jev API와 현재 추론 인프라의 포함 여부, 기간 사이 변경을 설명하는 자료. |
| ISO 27001 | 이번에 읽은 공개 자료에서 인증서를 확인하지 못했다. | 보유 여부, 인증 범위·유효기간·인증기관. 미확인은 미보유의 증명이 아니다. |

위 표의 계약 근거는 [MCA 4·10·12장](https://typesafe.ai/legal/mca), [DPA 1~5장과 Schedule I](https://typesafe.ai/legal/data-processing), [기업용 ZDR 안내](https://docs.typesafe.ai/legal)다. 공개 보안 설명과 보고서 목록은 각각 [Controls](https://trust.typesafe.ai/controls), [Resources](https://trust.typesafe.ai/resources)에서 확인했다. SOC 2는 감사보고서이며, 목록 확인으로 감사 의견이나 현재 Jev의 보안 적합성까지 검증한 것은 아니다.

**검토 판단:** 보안 자료가 전혀 없는 업체라고 볼 근거는 없다. 반면 학습 제한·암호화·SOC 2 목록만으로 우리 메일 전송의 법적 근거나 삭제 보장을 확보할 수는 없다. 계약과 실제 처리 흐름을 함께 확인해야 한다.

## 4. 한국법에 맞춰 남은 검토

### 4.1 처리 역할과 메일 속 제3자 정보

계정 소유자와 메일에 등장하는 고객·직원·거래처는 다른 정보주체일 수 있다. 계정 연결 동의와 각 정보의 수집·이용 근거를 구분해야 한다. 회사가 처리 목적을 정하고 Uteum-Mail에 맡기는 구조에서는 회사 → Uteum-Mail → AI 업체의 위탁·재위탁 관계를 검토한다. 계정 소유자 한 사람의 승인으로 회사 자료의 처리 권한까지 확인됐다고 판단하지 않는다. [개인정보보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1025128631), [제26조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029331867)

**검토 판단:** 서비스가 지시한 메일 분석만 수행하는 범위와 공급자가 자기 목적에 자료를 사용하는 범위를 나눠 역할을 판단해야 한다. API를 이용한다는 사실만으로 위탁 또는 제3자 제공의 분류가 확정되지는 않는다. 우리 고객 계약과 TypeSafe의 telemetry 실제 내용을 확인할 자료가 아직 없다.

### 4.2 위탁 계약과 수탁자 감독

법 제26조와 시행령 제28조는 목적 외 처리 제한, 보호조치, 위탁 목적·범위, 재위탁 제한, 감독, 책임에 관한 문서와 수탁자 공개를 요구한다. 공개 대상에는 재수탁자도 포함된다. **영문 DPA라는 명칭보다 이 항목과 실제 처리 내용의 일치가 중요하다.** [법 제26조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029331867), [시행령 제28조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0028&lsiSeq=286175&urlMode=lsScJoRltInfoR)

TypeSafe의 감사 조건·재위탁 승인·배상 제한을 국내 의무와 대조하고, 부족한 내용은 주문서나 별도 약정으로 보완할 수 있는지 확인하는 안을 추천한다. 표준 계약이 곧 위법하다는 판단이나, 추가 약정이 체결됐다는 기록은 아니다.

### 4.3 국외 이전 근거와 안내

동의만이 유일한 이전 근거는 아니다. 정보주체와의 계약 체결·이행에 필요한 처리위탁·보관에는 법이 정한 공개·알림 경로도 있다. 다만 메일에 등장하는 모든 사람을 우리 서비스의 계약 당사자로 볼 수 없으므로 이 근거를 일괄 적용하지 않는다. [제28조의8 제1항](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029331979)

실제 안내에는 이전 정보 항목, 국가, 시기·방법, 수령자·연락처, 목적·보유 기간, 거부 방법과 효과 등을 실제 흐름에 맞춰 적어야 한다. 현재는 계정별 ZDR·처리 지역·보유 기간이 미확인이라 완성된 국외 이전 안내를 작성할 수 없다. SOC 2 자료와 EU SCC만으로 한국법의 이전 근거를 대신한다고 보지 않는다. [제28조의8 제2항](https://law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1033215841)

### 4.4 주민번호와 건강정보 및 결제 정보

주민등록번호는 일반적인 동의만으로 처리할 수 없으며 법에서 허용하는 제한된 근거가 필요하다. 이름·전화번호를 지운 뒤에도 본문의 계약·주소·서명·인용문·첨부에서 개인을 식별할 수 있는지 검토해야 한다. [제24조의2](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1020399435)

**추천안:** 주민번호, 건강정보, 결제 인증값 등 고위험 자료의 외부 분석 제외 범위와 누락 검출 시 동작을 먼저 정한다. 결제 정보 전체를 법률상 민감정보로 일괄 분류하지는 않는다. 단순 문자열 마스킹만으로 자료 전체가 익명화됐다고 가정하지 않는다. 이는 아직 선택하지 않은 처리 범위와 구현 기준이다.

### 4.5 사고 통지와 삭제

우리의 신고·고객 통지 절차는 업체의 계약상 72시간 통지와 별도로 설계해야 한다. 시행령 제39조는 유출등 인지 후 72시간 이내 정보주체 통지와 예외를 정한다. 제40조는 1천명 이상, 민감정보·고유식별정보, 외부 불법 접근에 의한 유출 등의 신고 요건과 인지 후 72시간 기한, 미확인 내용의 우선 신고 및 예외를 규정한다. 업체와 우리의 인지 시점을 같은 시각으로 가정하거나 업체 통지만 기다리는 절차는 적합성을 확인할 수 없다. [시행령 제39·40조](https://law.go.kr/lsLinkCommonInfo.do?lspttninfSeq=67073)

2026-09-11 시행된 제39조의2·3에는 유출 가능성의 통지 요건과 시기·방법도 있다. 불법 접근으로 유출이 의심되지만 정보주체를 특정하기 곤란한 경우, 일부 유출 사실에서 다른 정보주체의 유출 가능성이 인정되는 경우 등 법정 요건에 해당하면 정해진 기산점부터 72시간 내 가능성 통지를 검토해야 한다. 단순한 의심 모두에 동일한 의무가 생긴다고 일반화하지 않는다. [시행령 제39조의3](https://law.go.kr/lsLinkCommonInfo.do?lspttninfSeq=67073), [법제처의 제39조의2·3 설명](https://www.easylaw.go.kr/CSP/CnpClsMain.laf?ccfNo=3&cciNo=2&cnpClsNo=3&csmSeq=1257&menuType=cnpcls&popMenu=ov)

삭제 범위는 원문·첨부·요약·임베딩·분류·캐시·작업 큐·실패 큐·로그·백업과 외부 업체의 자료를 포함해 점검하는 안을 추천한다. 연결 해제 후 새 수집 중단, 이미 저장된 자료의 삭제, 공급자 삭제 완료, 원래 메일 서비스의 원본 삭제는 효과가 다르다. 보관 기간과 삭제 소요 시간을 확인하기 전에는 즉시 완전 삭제를 약속하지 않는다. 이 범위는 [기획서 10장](07-웹앱-기획서-v1.6.md)의 자료 관리 원칙을 구체화한 점검 제안이다.

### 4.6 가입·시작 설정의 법률 검토 질문

사용자가 2026-10-03 정리한 가입·연결·시작 설정의 기본 흐름은 [기획서 7.1](07-웹앱-기획서-v1.6.md#71-처음-사용하기)에 반영했다. 아래는 적용 근거와 실제 운영을 확정하기 위한 질문이며, 법률 검토 완료나 회사 승인 확보를 뜻하지 않는다.

| 질문 | 검토에 필요한 구체적인 조건 |
| --- | --- |
| 1. 메일 속 다른 사람의 정보를 어떤 역할·근거로 처리하는가? | 계정 소유자·발신자·고객·회사 각각의 관계, 우리 서비스와 AI 업체의 처리 목적, 위탁·재위탁 여부와 정보주체의 권리 행사 경로 |
| 2. 업무용 사용자의 권한 진술을 어디까지 신뢰할 수 있는가? | 회사 정책·승인과 개인 진술의 차이, 기본 메일 처리와 외부 AI 처리 각각의 권한, 명시적 금지·미확인 때 허용 가능한 처리 범위. ‘메일만 보기’도 우리 서버 수집을 포함함 |
| 3. 국외 이전에 어떤 근거를 적용하며 업체 변경은 어떻게 처리하는가? | 동의 기반 이전의 고지·재동의, 계약 체결·이행에 필요한 위탁·보관 경로의 요건. 선택형 AI의 실제 필요성과 메일 속 다른 정보주체에게도 적용 가능한 근거를 따로 판단 |
| 4. 한 화면에서 필요한 동의를 각각 선택할 수 있는가? | 동의 전 안내, 항목별 구분·선택·거부와 개별 기록, 거부 시 이용 가능한 기능. 시작 버튼과 로그만으로 동의 요건이 충족됐다고 보지 않음 |
| 5. 자료별 처리 근거·보유 기간을 어떻게 구분하는가? | 가입 정보·메일 메타데이터·본문·첨부·분류·요약·임베딩·로그·백업별 목적·기간·삭제와 외부 업체의 완료 확인. 필요한 가입 정보의 계약 이행 근거를 전체 메일 처리에 확대 적용하지 않음 |

개인정보 처리방침은 공개 문서로 제공하고, 별도 동의가 필요한 처리는 구분한다. 전자적 선택도 동의 수단이 될 수 있으나, 필요한 항목을 명확히 알린 뒤 사용자가 각각의 선택을 할 수 있어야 한다. [개인정보보호법 제22조](https://law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1022694673), [제30조](https://www.law.go.kr/LSW//lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0030&lsiSeq=283839&urlMode=lsScJoRltInfoR), [시행령 제17조](https://www.law.go.kr/LSW//lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0017&lsiSeq=289537&urlMode=lsScJoRltInfoR)

동의를 근거로 하는 국외 이전은 항목·국가·시기와 방법·수령자와 연락처·목적과 보유 기간·거부 방법과 절차 및 효과를 사전에 알리고, 그 사항이 변경될 때 다시 알리고 동의를 받는 절차를 검토한다. 다른 법적 근거의 적용 여부를 동의 화면의 편의만으로 결정하지 않는다. [개인정보보호법 제28조의8](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=08&joNo=0028&lsiSeq=283839&urlMode=lsScJoRltInfoR)

Google 연동의 앱 내 안내는 일반 사용 흐름에서 수집·사용·공유 내용을 명확히 보여주고 동의로 이어지도록 구성한다. 제공사 인증만으로 메일을 수집하지 않고 시작 설정까지 기다리는 것은 이 프로젝트에서 채택한 흐름이며, Google이 동일한 화면 수나 순서를 지정했다는 의미는 아니다. [Google Workspace 사용자 데이터 정책](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)

## 5. GDPR 적용과 국제 이전

유럽 국적 고객이 있다는 사실만으로 적용 여부를 확정하지 않는다. EU 내 사업장 관련 처리, EU 내 개인을 대상으로 하는 상품·서비스 제공이나 행동 관찰 등의 실제 조건을 확인한다. 적용되는 경우 controller·processor 역할, 처리 근거, 안내·권리 행사·안전조치·기록 등을 검토해야 한다. 가명화·암호화된 자료도 다시 식별할 수 있으면 개인정보다. [유럽연합 집행위원회 GDPR 적용 설명](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/application-gdpr_en)

TypeSafe DPA 6.2는 controller → processor의 SCC Module 2와 processor → subprocessor의 Module 3를 포함한다. 우리 역할과 이전 구조에 맞는 모듈·부속서·보안조치가 실제 계약에 적용되는지 확인해야 한다. Schedule I의 정보주체·민감정보 기재와 계약 종료 후 반환·삭제 조건도 대조한다. [TypeSafe DPA](https://typesafe.ai/legal/data-processing)

**검토 판단:** SCC를 사용한다면 이전 목적국의 법·관행과 수령자가 SCC를 지킬 수 있는지 평가하는 TIA가 필요하다. 처리 사슬·정부 접근·재이전과 필요한 보완조치를 검토하고 문서화해야 하며, SCC가 있다는 사실만으로 완료되지 않는다. [집행위원회 SCC 문답 40·41](https://commission.europa.eu/law/law-topic/data-protection/international-dimension-data-protection/new-standard-contractual-clauses-questions-and-answers-overview_en)

국외 이전 평가를 위한 입력 자료와 EU 대상 제공 범위는 아직 확정되지 않았다. 따라서 이번 검토는 GDPR 준수 판정이 아니다.

## 6. 메일 제공사 정책

### 6.1 Gmail

메일 생산성 향상과 생성형 AI 요약은 허용 사례에 포함되지만, 데이터와 파생 정보의 사용·전송·사람의 열람은 Limited Use 조건을 따라야 한다. 특정 이용자의 개인화 범위를 넘어서는 AI 모델 생성·학습·개선에 사용하는 방식에는 제한이 있다. 외부 처리업체도 정책을 지켜야 한다. [Google Workspace 사용자 데이터 정책](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)

**검토 판단:** TypeSafe의 학습 제한만 확인해서는 충분하지 않다. telemetry가 Gmail에서 파생된 정보인지, 어떤 제품 개선에 사용하는지, 익명화와 목적 제한을 충족하는지 확인해야 한다. 문구만으로 정책 위반을 확정하지는 않지만, 공급자의 무제한 활용 문구를 그대로 수용할 근거도 부족하다. 외부 처리 설명은 처리방침뿐 아니라 앱의 정상 이용 흐름에서 동의 전에 안내해야 한다. [같은 정책의 Transparent notice와 Limited use 절](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)

`gmail.readonly`·`gmail.modify` 등은 제한 권한이다. 제한 권한 데이터를 서버에 저장하거나 전송하면 보안 평가 대상이며, 공개 SaaS가 조직 내부 앱 예외에 해당한다고 가정할 수 없다. 연간 평가 비용과 일정을 확인해야 한다. TypeSafe의 SOC 2 보고서가 우리 앱의 이 평가를 대신하지는 않는다. [Gmail 권한](https://developers.google.com/workspace/gmail/api/auth/scopes), [검증 요건](https://support.google.com/cloud/answer/13464321)

### 6.2 네이버와 다음 및 카카오메일

네이버의 공식 연결 안내에서 IMAP의 SSL 연결과 SMTP의 TLS 연결을 확인했다. 그러나 연결 안내는 메일을 외부 AI에 재처리하는 상용 SaaS의 모든 조건을 설명하는 문서가 아니다. [네이버 IMAP·SMTP 안내](https://help.naver.com/service/30029/contents/21351?osType=COMMONOS)

다음·카카오메일을 포함한 4종 지원 목표는 유지한다. 이번 조사로 각 제공사의 AI 재처리·상용 운영 허용 범위까지 확인하지 못했으며, Gmail 정책을 그대로 적용하거나 외부 연결 가능성만으로 승인됐다고 기록하지 않는다. 실제 커넥터의 적용 약관·권한·인증·호출 제한과 고객 자료 취급 조건은 제공사별 확인이 남아 있다.

## 7. 생성 LLM과 임베딩 및 내부 저장 경로

### 7.1 OpenAI API를 사용하는 경우

OpenAI 공식 문서는 API 자료의 기본 학습 미사용, 기본적으로 최대 30일 보관하는 남용 감시 로그와 예외, 사전 승인 대상 ZDR·Modified Abuse Monitoring을 설명한다. 실제 모델·기능·계정에 적용되는 조건을 확인해야 한다. [OpenAI API 데이터 관리](https://developers.openai.com/api/docs/guides/your-data)

| 경로 | 확인한 공개 조건 | 우리 프로젝트에 대한 영향 |
| --- | --- | --- |
| `/v1/embeddings` | 남용 감시 보관 30일, 별도 application state 없음, ZDR 적용 가능으로 안내. | 본문을 숫자 벡터로 바꾸는 요청도 입력 본문을 전송한다. 모델 추천만으로 실메일 호출이 승인된 것은 아니다. |
| `/v1/responses` | 기본 또는 `store=true`의 application state는 최소 30일 저장된다고 설명하며, 남용 감시와 별도다. | `store=false` 하나로 전체 무보관을 보장하지 않는다. background·파일·도구·캐시 등 기능별 예외를 확인한다. |
| ZDR | 승인·추가 조건이 필요하며 기능과 모델별 제한이 있다. | 계약·계정 설정·지원 기능·법적 예외를 실제 호출과 대조해야 한다. |
| 한국 리전 | 표에 저장 지역 지원은 Yes, 지역 내 추론 처리는 No로 표시된다. | 한국 저장 선택만으로 한국 안에서만 처리한다고 안내할 수 없다. 비미국 리전의 승인·추가 계약 조건도 확인한다. |

위 조건은 [공식 문서의 Endpoint별 보관 표와 Data residency](https://developers.openai.com/api/docs/guides/your-data)를 기준으로 한다. 한국 리전에서도 지역 밖 처리·임시 저장과 시스템 데이터의 예외가 설명된다.

**미확인:** 기획서의 Luna·Sol 명칭에 대응하는 실제 API 모델 ID·엔드포인트·중개 사업자, 우리 계약과 계정 설정. 이 보고서가 모델 배분을 바꾸거나 OpenAI API 계약을 채택하는 것은 아니다. 임베딩 후보 `text-embedding-3-small` 역시 기존대로 사용자 선택 전이다.

### 7.2 중개 API와 우리 인프라

Jev나 생성 LLM을 중개 API로 호출하면 중개 업체의 보관·로그·재위탁 계약도 추가로 확인해야 한다. TypeSafe 직접 API의 설명을 중개 경로 전체에 적용하지 않는다. 현재 호출 경로는 미확인이다.

우리 시스템도 DB·첨부 저장·SQS·실패 큐·CloudWatch·추적·백업에서 메일 본문이나 파생 자료를 보관할 수 있다. 이들에 실제 어떤 필드를 넣는지, 지역·접근 권한·삭제 절차가 무엇인지 점검하는 안을 추천한다. 특히 API 키·메일 앱 비밀번호·OAuth 토큰은 AI 입력과 로그의 검토 범위에 명시해야 한다. 지역과 최소 보관 정책은 아직 확정하지 않는다.

| 자료 | 먼저 확인할 범위 |
| --- | --- |
| 모델 입력 | 제목·본문·관련 대화·사용자 규칙·첨부 추출문·시간·식별자 중 작업에 필요한 최소 범위. |
| 모델 출력과 검색 자료 | 요약·초안·분류·근거·임베딩의 개인정보 포함 여부, 사용자·계정 간 권한, 삭제 전파. |
| 운영 자료 | 오류·요청 추적·평가 기록·큐·백업에 본문이 복제되는 경로와 실제 보관 기간. |
| 계정 해제와 삭제 | 새 호출 중단, 진행 중 작업·재시도·늦게 도착한 결과·복원 이후 자료 재생성을 막는 처리. |

이 표는 구현 완료가 아닌 점검 제안이다. 기존 스택과 [기획서 자료 관리 원칙](07-웹앱-기획서-v1.6.md)은 유지한다.

## 8. 실제 메일 전송 전에 준비할 자료

아래는 이번 검토의 추천 산출물이다. 업체 확인만으로 우리 서비스의 처리 근거·화면 안내·구현 검증을 대신하지 않는다.

1. 실제 데이터 흐름과 처리 역할: 고객 → 우리 서버 → AI·임베딩·중개 업체 → 재수탁자 → 로그·백업을 국가·목적·항목별로 기록한다.
2. 계약 증빙: 우리 계약 주체에 적용되는 DPA·주문서·ZDR 약정·재위탁 승인·변경 통지·반환과 삭제·사고 책임을 대조한다.
3. 법적 근거와 이용자 안내: 국내 위탁·국외 이전·메일 속 제3자 정보의 처리 근거와 공개·동의·거부·권리 행사 경로를 정한다. GDPR 적용 시 이전 평가도 포함한다.
4. 보안 자료: SOC 2 원문·감사 범위·변경 자료, API와 재수탁자 경로의 암호화·접근 통제·침투 시험 자료를 확인한다.
5. 삭제와 사고 대응 절차: 항목별 기간·삭제 완료 확인·외부 업체 협조·고객 통지·신고·연락망을 정한다.
6. 검증 결과: 합성 자료로 입력 최소화·분석 제외·권한 격리·로그 노출·삭제와 늦은 결과 처리를 먼저 확인하고, 실제 자료의 시험 범위는 별도 선택한다.
7. 메일 제공사 자료: Gmail의 최소 권한·Limited Use·보안 평가와 다른 제공사의 실제 운영 조건을 확인한다.

공급자가 필요한 조건을 제공하는 경우의 비용과 계약 협의 기간은 아직 알 수 없다. 제공하지 못하면 실메일 Jev 평가를 보류하는 안을 추천하며, 기존 생성 모델 경로도 별도로 같은 확인을 거친다. 직접 실행 모델은 외부 전송을 줄이는 대안이지만 품질·연산비·운영 부담을 다시 비교해야 하므로 이번에 채택하지 않는다.

## 9. 업체에 확인할 질문

아래는 문의 준비용이며 발송하지 않았다. 실제 고객 메일·토큰·계약 원문을 예시로 첨부하지 않고 처리 항목과 요구 자료를 설명하는 방식으로 문의할 수 있다.

| 질문 | 필요한 답변이나 증빙 |
| --- | --- |
| 우리 메일 SaaS에 어느 계약과 DPA가 적용되는가? | 우리 법인·계정·API 경로를 지정한 적용 문서와 버전, 한국 고객 자료 처리에 필요한 보완 가능 여부. |
| 메일 속 거래처·직원 정보와 건강정보 등은 어떤 범위로 처리할 수 있는가? | 실제 정보주체·항목·목적을 반영한 부속서와 제한·보호조치. 주민번호의 국내 처리 근거는 우리 쪽에서 별도로 확인한다. |
| ZDR의 정확한 적용 범위와 예외는 무엇인가? | 입력·출력·telemetry·오류·캐시·백업·지원 자료와 모든 재수탁자에 대한 표, 활성화 증빙·가격·최소 약정. |
| Telemetry에 무엇을 남기고 무엇에 사용하는가? | 샘플 필드·식별 가능성·익명화 방법·기간·사람의 접근·제품 개선 범위, Gmail Limited Use 충족 설명. |
| 요청은 어느 업체·지역으로 전달되는가? | AWS·Modal·Nebius·CoreWeave의 실제 역할과 리전, 장애 전환·직원 접근·재이전·목록 변경 통지. |
| 데이터를 언제 완전히 삭제하고 반환하는가? | 계약 종료·개별 고객 삭제·계정 해제 시의 절차, 백업 만료, 삭제 확인서, 법령 보존 예외와 대상. |
| Jev가 SOC 2 감사에 포함되는가? | 2026 보고서 원문·감사 기간·범위·예외·최근 변경 설명, ISO 인증의 보유 여부와 범위. |
| 전송·저장·접근 보안은 어떻게 검증할 수 있는가? | API·재수탁자 간 암호화, 키 관리, 테넌트 격리, 접근 기록, 최근 침투 시험과 미해결 사항. |
| 사고와 삭제·권리 행사 요청에 어떻게 협조하는가? | 상시 연락처, 초기 통지·추가 보고·증거, 감독·감사 예외, 협조 비용, 배상·보험 조건. |
| EU 고객 자료를 처리할 경우 어떤 이전 평가 자료를 제공하는가? | 적용 SCC 모듈·부속서, 정부 접근과 법·관행 평가 자료, 보완조치·변경 시 재평가 지원. |

공개 자료의 재검토와 실제 계약 자료 확보를 마친 뒤, 실메일 허용 범위·처리업체·보관과 삭제 기준을 추천안·대안·비용 영향과 함께 사용자에게 제시한다. 사용자 선택 전에는 이번 추천을 기획서의 확정 사항으로 반영하지 않는다. 선택이 이루어지면 관련 문서를 최신화하고, 후속 결정 목록에는 아직 선택이 필요한 항목만 남긴다.
