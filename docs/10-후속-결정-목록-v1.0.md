## 1. 초기 구현과 운영 전에 결정할 항목

한 번에 모든 답을 요구하지 않는다. 아래에는 남은 세부 선택만 기록하며, 실제 서버·AI 연결과 사용자 베타에 필요한 항목을 해당 시점에 질문한다. 화면의 가상 체험에 필요한 기준은 관련 프로토타입 문서를 따른다.

### 1.2 DB 호스팅 사업자와 운영 예산

- **추천안:** 공유 환경은 Neon·Supabase 등 무료 관리형 후보를 용량·휴면·지원 버전·pgvector·복구 기능·리전으로 비교한 뒤 선택한다. 실제 사용자 베타에서는 복구 목표를 충족하는 최소 비용 요금제를 고른다.
- **대안:** 무료 한도나 복구 기능이 맞지 않으면 유료 관리형 또는 기존 VM의 직접 운영을 비교한다. 직접 운영은 백업·패치·장애 대응 시간을 함께 계산한다.
- **확인:** 전체 인프라 월 상한과 DB 몫, 연결 계정·메일·벡터 저장량, 연산·전송량, 접속 지연, 실제 복원 가능 범위.
- **결정할 질문:** 공유 DB 사업자·지역·요금제와 초기 월 예산을 무엇으로 정할지?
- **결정 시점:** 화면 검토 이후 DB가 필요한 공유 환경을 만들기 전. [무료 대안과 비용 계산](08-Java-버전과-AWS-비용-검토-v1.0.md)

### 1.3 작업 전달과 복구의 세부 계약

- **추천안:** 작업 종류별 처리 시간과 전체 비용 예산을 기준으로 숨김 시간·연장 주기·재시도 횟수·실패 큐 전환·결과 만료를 정한다. 제공사·모델 제한과 취소 후 결과의 처리도 함께 정의한다.
- **대안:** 모든 작업에 동일한 한도를 두면 구현은 단순하지만 긴 AI 작업과 짧은 동기화 작업에 불필요한 재시도·대기가 생길 수 있다.
- **확인:** 서버와 AI의 인증 방식, 메시지·결과 계약 버전, outbox 재발행, 실패 작업의 수동 재처리 권한·기록, 재전달 시 중복 방지.
- **결정할 질문:** 작업별 제한 값과 실패·취소·만료·인증 계약을 어떻게 정할지?
- **결정 시점:** 영구 작업 처리 구현 전. [AWS outbox 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

### 1.4 VM 사업자와 자원 배치 및 담당자

- **추천안:** DB 지역과 통신 비용을 함께 보고 VM 사업자·지역·규모를 선택한다. Spring API·메일 동기화·AI HTTP·AI 워커의 CPU·메모리·연결 한도를 명시하고 영역별 유지보수 책임을 정한다.
- **대안:** 한 VM에 함께 배치하면 고정비가 낮아질 수 있으나 서버 장애를 공유한다. 여러 VM은 장애 영향과 자원 경합을 줄이는 대신 비용·운영 요소가 늘어난다.
- **확인:** 최소 자원·배포 절차·장애 대응·호환성 시험·DB 복구를 맡을 담당자와 월비용.
- **결정할 질문:** VM 사업자·자원·프로세스 배치와 각 영역의 주담당을 누구로 정할지?
- **결정 시점:** 공유 배포 환경을 만들기 전.

### 1.5 검색 세부 범위와 임베딩 모델

- **추천안:** 메일 제목·본문을 우선 색인하고 현재 대화는 직접 조회한다. 필요한 과거 대화는 키워드·의미 검색으로 보강한다. 임베딩은 OpenAI `text-embedding-3-small`의 기본 1,536차원을 실제 의미 검색 기술 검증의 첫 비교 기준으로 제안한다.
- **대안:** BAAI `bge-m3` 직접 실행은 외부 임베딩 API 의존성을 줄이지만 모델·자원·배포 관리가 추가된다. 첨부 텍스트·OCR까지 처음부터 색인하면 검색 범위와 함께 파싱·저장·갱신 비용도 늘어난다.
- **확인:** 한국어 메일 검색 품질, 외부 본문 전송 조건, 색인할 과거 이력·제외 범위, 입력 분할·검색 후보 수, 모델·차원 변경 시 재색인 비용, 권한·삭제·변경 반영.
- **결정할 질문:** 실제 의미 검색의 색인 대상을 제목·본문과 대화 문맥으로 정하고, 위 임베딩 모델을 첫 시험 기준으로 사용할지?
- **결정 시점:** 의미 검색 프로토타입에 실제 임베딩을 연결하기 전. [사용 방식과 후보 설명](06-기술-스택-선택-비교-보고서-v1.0.md#91-pgvector-검색과-임베딩-사용-방식)

### 1.6 첨부·관찰 데이터의 보관·수집 설정과 비용 한도

- **추천안:** 첨부의 보관·삭제는 원본 메일과 계정 연결 해제 정책에 맞춘다. 관찰 데이터는 장애·비용·품질 확인에 필요한 보관 기간과 추적 수집률을 정하고, Spring과 AI 사이 작업 ID가 이어지는 구간을 우선한다.
- **대안:** 모든 본문·도구 입력·실행 단계를 장기간 저장하면 조사 범위가 넓어지지만 민감정보 보관량과 저장·조회 비용이 증가한다.
- **확인:** 첨부 버전·삭제 유예, 로그의 메일 본문·인증 토큰 제외, 보관 기간·추적 수집률, 경보 수신 대상, OpenTelemetry 추적 저장 대상과 월비용 상한.
- **결정할 질문:** 첨부·로그·추적의 보관·삭제 기간, 추적 수집률·경보 수신 대상·저장 대상과 비용 한도를 어떻게 정할지?
- **결정 시점:** 외부 저장·관찰 서비스를 구성하기 전.

### 1.7 백업 구현과 복구 검증 범위

- **추천안:** DB 사업자의 시점 복구 기능을 먼저 확인하고, 부족하면 연속 WAL 보관 등 대안의 비용·운영 부담을 비교한다. DB·첨부·작업·외부 발송 기록을 어디까지 복구할지 정하고 전체 복원 절차를 시험한다.
- **대안:** 정기 덤프는 단순한 개발 데이터 복원에 쓸 수 있으나 덤프 사이의 변경을 복구할 수 없다. 복구 가능한 최신 시점과 서비스 재개 시간으로 적합성을 판단한다.
- **확인:** 백업 주기·저장 위치·접근 권한·실패 경보·복원 담당자, 데이터 삭제와 백업의 관계, API 가용성의 측정 경로·실패 정의·계획 점검 처리.
- **결정할 질문:** 호스팅에 맞는 백업 방식과 DB·첨부·발송 기록의 복구·측정 범위를 어떻게 정할지?
- **결정 시점:** 실제 사용자 베타 운영 전. [기획서 운영 기준](07-웹앱-기획서-v1.6.md#132-기술-구성과-앱-확장의-검증-기준)

### 1.10 홈 캘린더의 세부 표시와 날짜 선택 동작

- **결정할 항목:** 기본 월간·주간 보기, 달력에 표시할 일정·업무·메일의 범위, 날짜 선택 시 열 정보.
- **추천안:** 월간 보기를 기본으로 하고 확정된 일정·기한만 간결하게 표시한다. 홈 메일 목록은 사용자가 요청한 오늘의 보낸 사람·제목 표시를 유지한다. 날짜 이동은 보관 자료 조회로 구현해 추가 AI 호출을 줄이는 방향으로 제안한다.
- **대안:** 주간 보기는 하루의 시간대를 자세히 볼 수 있지만 한 번에 확인하는 기간이 짧다. 메일 수신일 중심의 달력은 메일 찾기에 집중할 수 있으나 일정·업무 표시와 목적이 달라진다. 외부 캘린더 동기화를 함께 도입하면 별도 권한·실패 처리·운영 부담을 검토해야 한다.
- **확인:** 사용자가 달력에서 확인하려는 정보, 일정 자료의 출처, 일정 없음·미연동 상태, 모바일 표시, 날짜 선택 동작. 공급자별 외부 연동 지원은 미검증이다.
- **결정할 질문:** 월간 보기와 확정 일정·기한 표시를 기본으로 할지, 주간 또는 메일 수신일 중심으로 할지? 날짜를 누르면 어떤 정보를 확인할지?
- **결정 시점:** 실제 프로젝트의 홈 캘린더 구현 전. [UX·UI 문서의 메인 홈 기준](17-사용자-UX-UI-설계와-요구사항-v1.0.md#32-메인-홈--ux03)

## 3. 웹 검증 이후 결정할 항목 — 보류

### 3.1 앱 출시와 지원 범위

- **결정할 항목:** 앱 출시 여부·시점·OS·프레임워크·기기 캘린더 지원 범위.
- **추천안:** 웹의 반복 사용·동기화 신뢰성·비용·모바일 기능 수요를 확인한 뒤 React Native·Expo를 첫 후보로 비교한다.
- **대안:** Flutter 또는 Swift/Kotlin. 웹과의 코드 공유 범위·OS 기능·클라이언트 유지보수 부담을 비교한다.
- **확인:** 메일 목록·본문·편집, 첨부·푸시·캘린더 연동의 실제 기기 시험과 플랫폼별 사용자 수요.
- **결정 시점:** 웹 결과를 바탕으로 앱 검토를 재개할 때. 현재 선택은 보류 상태다.

### 3.2 인프라 고도화의 도입 범위와 시점

세부 결정은 보류한다. 초기 PostgreSQL 호스팅의 유료 확장 또는 RDS 이전, ECS/Fargate·Multi-AZ·자동 확장·별도 검색 서비스 등의 도입 여부·범위·시점은 프로토타입 이후 실제 병목·복구 요구·비용을 확인한 뒤 결정한다. DB 이전 시 허용할 중단 시간과 복구 절차도 함께 선택한다. 항목별 추천안·대안·재검토 조건은 [인프라 고도화 계획](09-인프라-고도화-계획-v1.0.md)을 따른다.
