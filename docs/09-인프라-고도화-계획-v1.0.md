# 인프라 고도화 계획 v1.0

- 작성일: 2026-10-01
- 최신 개정일: 2026-10-01
- 상태: 채택한 초기 구성을 바탕으로 확장 후보와 재검토 조건을 정리한 문서. RDS·ECS·Multi-AZ 등 고도화의 세부 결정은 보류했다.
- 기준: 웹 우선, Spring Boot와 Python/FastAPI 분리, PostgreSQL 사용

## 1. 진행 원칙

초기에는 메일 연결·동기화·AI 품질과 사용자 가치를 확인한다. **ECS 등 배포 인프라의 고도화는 실제 병목과 운영 부담이 확인될 때 다시 선택한다.** 사용자 수 하나로 도입 시점을 정하지 않고 지연·오류·대기열·DB 자원·복구 시간·비용을 함께 확인한다.

초기는 PostgreSQL 18.x 로컬 개발과 공유 데모·소규모 베타의 무료 관리형 DB 우선 검증 방향을 채택했다. RDS 전환은 수요·용량·복구 요구·관리 부담이 커지는 단계에서 검토한다. 구체적 사업자·요금제·전환 시점은 미확정이며, 고도화의 세부 선택은 기획서 정리와 프로토타입 이후 필요 시점에 재개한다.

초기 VM·Docker 구성과 SQS Standard를 채택했다. 첨부는 비공개 S3, 기본 로그·지표는 CloudWatch, 필요한 구간의 추적은 OpenTelemetry를 기준으로 한다. 유휴 비용·무료 DB 한도·대안의 유지보수는 [Java 버전과 AWS 비용 검토](08-Java-버전과-AWS-비용-검토-v1.0.md), 남은 사업자·범위·비용 선택은 [후속 결정 목록](10-후속-결정-목록-v1.0.md)을 따른다.

## 2. 초기 운영에 포함할 기반

고도화 시점을 늦추더라도 사용자 데이터와 저장된 작업을 복구할 수 있어야 한다. 다음은 초기 구현·운영에서 구체화할 요구이며 제품 선택은 별도다.

- Spring과 AI 작업의 CPU·메모리·연결 수를 제한하고 AI 장애 때 일반 메일 경로가 계속 동작하는지 확인한다.
- 작업 ID·현재 상태·시도 횟수·결과 적용 기록을 저장하고, 재시작·중복·늦은 결과·권한 변경을 검증한다.
- DB와 첨부의 백업 범위·보관 기간·복원 절차를 정하고 실제 복원을 확인한다.
- API 오류·큐 대기·동기화 지연·DB 공간·AI 사용 비용을 관찰한다. 로그의 보관량과 비용도 제한한다.
- 배포 실패 시 돌아갈 버전과 DB 변경 절차를 준비한다.

하나의 서버에서 프로세스만 분리하면 서버·디스크·네트워크 장애는 공유한다. 초기에 허용할 중단 시간과 복구 방법을 정하고, 필요한 가용성이 단일 서버로 충족되지 않을 때 복수 서버를 검토한다.

## 3. 고도화 후보와 재검토 조건

| 항목 | 다시 검토할 상황 | 추천 방향 | 대안과 비용·운영 차이 |
| --- | --- | --- | --- |
| ECS와 Fargate | 배포·재시작 관리가 반복 부담이 되거나 워커만 따로 증설할 필요가 커짐 | 컨테이너와 상태 저장 책임을 정리한 뒤 ECS 서비스·Fargate 검토 | EC2와 Docker를 계속 쓰면 단순한 구성을 유지할 수 있으나 서버 관리·교체를 직접 담당. Fargate도 실행 자원·로그·네트워크 등의 비용이 있음 |
| API 복제와 로드밸런서 | 서버 한 대의 배포·장애가 허용 중단 시간을 넘거나 API 처리량 부족이 확인됨 | API를 복제하고 상태 검증·연결 종료·배포 중 요청 처리를 시험 | 단일 서버 증설은 저렴하고 단순할 수 있지만 서버 장애 격리는 제공하지 않음 |
| 메일·AI 워커 자동 확장 | 오래된 대기 작업이 목표 시간을 지속 초과 | 작업 종류별 대기 시간과 제공사·모델 한도를 함께 보고 확장 | 고정 워커는 예측이 쉽지만 피크에 지연. 무제한 자동 확장은 모델 비용과 DB 연결을 급증시킬 수 있음 |
| 초기 PostgreSQL에서 RDS로 전환 | 무료 한도·휴면 조건·검색 부하·복구 요구·직접 운영 부담이 커짐 | 기존 호스팅의 유료 확장과 RDS 이전을 비교하고 작은 데이터로 복원·전환 시간을 미리 측정 | 같은 사업자 내 확장은 데이터 이전을 줄일 수 있음. RDS 이전은 메이저 버전·확장·권한·중단 시간·월비용 검토가 필요 |
| RDS Multi-AZ | DB 장애 복구 시간이 허용 범위를 넘거나 정식 운영의 가용성 요구가 높아짐 | 비용 견적과 장애 전환 시험을 거쳐 도입 | Single-AZ와 복원 절차는 기본 비용을 낮추지만 대기 DB로 자동 전환하지 못함. Multi-AZ의 단일 대기 DB는 읽기 확장용이 아님 |
| DB 증설·연결 관리 | 느린 쿼리 개선 후에도 CPU·메모리·I/O·연결 수가 병목 | 쿼리와 풀 제한을 먼저 확인하고 인스턴스 증설 검토 | 연결 프록시·복제본은 필요할 때 비교. 고정 비용과 운영 요소가 추가됨 |
| 검색·벡터 확장 | 관련 메일 검색의 품질 또는 지연 목표가 PostgreSQL 구성에서 충족되지 않음 | 인덱스·후보 필터·검색 범위·임베딩 비용을 먼저 측정 | 별도 검색·벡터 서비스는 독립 확장이 가능하지만 데이터 동기화·권한 필터·장애 대응이 추가됨 |
| Redis 등 캐시 | 반복 조회·임시 데이터가 확인된 병목 | 효과가 큰 범위부터 도입하고 무효화·장애 시 동작 검증 | 캐시 없이 DB·쿼리를 개선하면 구성은 단순하나 반복 부하 감소에 한계가 있을 수 있음 |
| 관찰 도구 확장 | 기본 로그·지표만으로 장애 구간을 찾기 어렵거나 호출 경로가 늘어남 | OpenTelemetry로 연결된 추적을 수집하고 저장·조회 도구 선택 | 수집 도구와 저장 도구는 별도. 수집률·보관 기간에 따라 비용이 달라짐 |
| 재해 복구 확장 | 리전 장애까지 복구 대상에 포함할 사업 요구가 생김 | 다른 리전의 백업·복원 시험부터 비용과 목표 검토 | 다중 리전 상시 운영은 복제·통신·정합성 관리가 크게 늘어남 |

ECS의 실행 환경과 RDS의 가용성 구성은 독립 선택이다. RDS를 먼저 채택해도 ECS를 함께 도입할 필요는 없다. Kubernetes·Kafka도 현재 채택 대상이 아니며 기존 구성으로 해결되지 않는 요구가 확인될 때 비교한다.

근거: [Fargate 요금 구조](https://aws.amazon.com/fargate/pricing/), [RDS Multi-AZ 단일 대기 DB](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html), [OpenTelemetry 역할](https://opentelemetry.io/docs/what-is-opentelemetry/). 도입 순서와 재검토 조건은 이 프로젝트에 대한 설계 추천이다.

### 3.1 PostgreSQL에서 RDS로 전환

데이터가 작고 계획된 쓰기 중단을 허용할 수 있는 단계에서는 덤프·복원 방식의 이전을 우선 검토한다.

1. 이전할 PostgreSQL 버전, pgvector 등 확장, 권한, 저장 용량을 확인하고 스키마와 데이터를 시험 복원한다.
2. API·메일 동기화·AI 결과 저장을 포함한 모든 쓰기를 중단하거나 마무리하고, 미완료 작업의 처리 방법을 정한 뒤 최종 데이터를 옮긴다.
3. 연결 대상을 변경하고 데이터 건수·제약 조건·권한·검색·초안·작업 재개를 확인한다. 첨부 파일은 DB 외의 저장 위치도 확인한다.
4. 전환 후 발생할 새 쓰기까지 보존할 수 있는 복구 절차를 준비한 뒤 서비스를 재개한다.

무중단이 필요해지면 지속 복제 등의 방법을 추가로 비교한다. 초기에는 같은 PostgreSQL과 호환되는 확장을 사용하고 SQL 변경 이력을 관리해 이전 가능성을 유지한다. 실제 이전 시간은 데이터량·인덱스·네트워크 조건에 따라 측정한다. [PostgreSQL 덤프·복원](https://www.postgresql.org/docs/current/backup-dump.html), [RDS PostgreSQL로 이전](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Procedural.Importing.html)

### 3.2 큐 전달 방식 변경

SQS Standard를 초기부터 채택했으므로 사용자 증가만을 이유로 큐 제품을 바꿀 필요는 없다. 워커 증설·배포나 전달 경로의 재구성이 필요할 때 작업 ID·Spring의 업무 최종 상태·결과 검증을 유지한다. 기존 소비자 종료·진행 작업 정리·미완료 작업 재개·중복 방지를 시험하고, 재전달 중 같은 작업이 두 워커에서 실행되는 상황도 검증한다.

## 4. 확장 시 유지할 가용성과 복구 목표

2026-10-01 사용자가 백업 7일 보관·실제 복원 시험, DB RPO 5분·RTO 1시간, 비공개 베타 API 월 99.5%·정식 월 99.9% 목표를 승인했다. 기준과 검증 조건은 [기획서 13.2](07-웹앱-기획서-v1.6.md#132-기술-구성과-앱-확장의-검증-기준)에서 관리한다. 목표 채택과 실제 달성은 구분한다.

무료 관리형 DB·단일 VM이 목표를 충족하는지 먼저 확인하고, 충족하지 못하면 목표를 유지할 운영 구성·비용을 제시한다. RDS 사용 자체로 달성을 보장하지 않으며 Multi-AZ도 잘못된 삭제를 되돌리는 백업을 대체하지 않는다. 구체적인 백업 방식·예산을 선택한 뒤 복원 시험으로 확인한다.

## 5. 고도화 결정 시 남길 기록

각 검토에서 현재 지표, 문제가 생긴 조건, 추천안과 대안, 예상 월 추가 비용, 전환·복구 절차를 제시한다. 사용자 선택을 받은 뒤 해당 항목만 확정한다. 앱 출시는 이 문서의 고도화 일정과 연결해 자동 진행하지 않으며 현재 보류 상태다.
