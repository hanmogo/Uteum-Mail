# GPT Decisions 라우팅 v1 — 요청과 평가 자료

- 작성일·공식 형식 확인일: 2026-10-29
- 상태: **요청 파일·합성 사례·오프라인 요청 조립기 준비. 실제 API 호출·한국어 성능·운영 임계값 검증 전**
- 준비 검사: 질문 10개·원래 의미 기준 보존, 개발·평가 후보 82개의 참조·기대값 형식, 모델용 요청 69개의 입력 격리·JSON 조립, 서버 전용 13개 요청 생성 생략, 한글 저장·기존 출력 파일 보존을 오프라인으로 확인했다. 서버 구현 시험이나 모델 정답률 측정은 아니다.
- 적용 범위: 자연어 요청에서 선택한 대화의 새 답장 초안을 직접 처리할 수 있는지 판단하는 A0 앞단 라우팅. A1 메일 중요도 분류·A2 업무 연결·A3 수신 관리의 개별 판단 시험은 별도다.
- 기준: [상세 설계 5.5](../12-에이전트+결정모델-세부-구조-v1.0.md#55-초기-라우팅-질문-명세-v1), [전체 사용자 시나리오](../05-전체-사용자-시나리오-v1.0.md), [기획서 검증 기준](../07-웹앱-기획서-v1.6.md#132-기술-구성과-앱-확장의-검증-기준)

## 1. 파일과 용도

| 파일 | 용도 |
| --- | --- |
| [API 요청](gpt-decisions-routing-v1.request.json) | 실제 전송할 본문 형식. Choice 2개·Predicate 8개와 합성 입력 |
| [개발 사례 34개](gpt-decisions-routing-v1.dev-cases.json) | 기존 Jev 사례와 같은 입력·의미 정답. 모델 평가 대상 29개, 서버 사전 분기 5개 |
| [분리 평가 후보 48개](gpt-decisions-routing-v1.eval-cases.json) | 다른 발화·대화·선택 참조를 사용한 합성 후보. 모델 평가 대상 40개, 서버 사전 분기 8개 |
| [오프라인 요청 조립기](prepare-gpt-decisions-request.mjs) | 사례 하나의 입력만 요청에 넣어 출력. 네트워크·API 키·과금 없이 실행 |
| [Jev 원본 요청](jev-routing-v1.request.json)·[사례](jev-routing-v1.cases.json) | 비교 기준으로 보존. 이번 작업에서 변경하지 않음 |

34개 개발 사례는 질문 작성에 사용한 자료다. 48개는 요청 변환 파일 작성 뒤 따로 만든 평가 후보지만, 같은 작성자가 같은 시나리오를 바탕으로 만든 **검수 전 합성 정답**이다. 대표성 있는 독립 시험이나 500개 대화 평가를 대신하지 않는다. 평가 전에 정답·자료 출처·표본·수용 기준을 검수하고 고정한다. 이 후보로 질문·임계값을 조정했다면 개발 자료로 전환하고 별도 평가 자료를 마련한다.

## 2. 질문 의미와 API 형식

- 모델·엔드포인트: `gpt-6-luna`, `POST https://api.openai.com/v1/decisions`.
- Jev의 공유 `state`를 `input[0].content[0]`의 `{"type":"input_json","data":...}`에 넣었다. 대화 이력의 `role` 값도 JSON 내부 자료이며 실제 시스템·개발자 메시지로 승격하지 않는다.
- 질문 객체의 키를 GPT 질문 배열의 고유 `name`으로 옮겼다. 기존 질문의 순서와 `instructions`를 보존했다.
- Choice 2개의 `criteria`를 `choices: [{value, description}]`으로 옮겼으며 선택지·순서를 보존했다.
- Noul 8개는 `predicate`로 옮겼다. 원래의 참·거짓 설명을 각 질문의 `instructions`에 그대로 추가했다. 같은 호출의 다른 답을 참조하지 않는다.
- 이 평가 요청은 `prompt_cache_options.mode = "explicit"`로 두고 캐시 경계는 지정하지 않아 캐시를 사용하지 않는다. 캐시 효과를 섞지 않는 시험 설정이며 운영 캐시 정책 확정이 아니다.

질문은 `route_candidate`, `reply_draft_requested`, `mail_lookup_requested`, `send_requested`, `mail_state_change_requested`, `persistent_rule_change_requested`, `subscription_change_requested`, `other_task_requested`, `draft_target`, `needs_interpretation`이다. 형식과 문구의 전체 명세는 요청 파일을 따른다.

## 3. 사례별 요청 만들기

저장소 루트에서 Node.js로 실행한다. 다음 명령은 파일만 만들며 API를 호출하지 않는다.

```bash
node docs/fixtures/prepare-gpt-decisions-request.mjs eval GD-EVAL-03 gpt-decisions-example.request.json
```

출력 파일을 생략하면 요청 JSON만 표준 출력으로 나온다. 출력 파일이 이미 있으면 덮어쓰지 않고 실패한다. `dev GD-DEV-03`으로 기존 복합 요청 사례도 준비할 수 있다.

조립기는 `input_data`만 공유 입력에 넣는다. 정답·사례 ID·태그·시나리오 ID·`server_context`·설명은 전송하지 않는다. `call_decisions=false`인 서버 시험 사례는 요청을 만들지 않고 종료 코드 2와 기대 경로를 알린다. 이것은 평가 자료의 호출 대상 구분이며 실제 서버 사전 분기를 구현하거나 검증한 결과가 아니다.

실제 API 호출은 계정 접근·크레딧 적용 조건·평가 예산을 확인한 뒤 별도 수행한다. API에 보내는 것은 조립된 요청 본문이며, 사례 파일 전체가 아니다. 요청 파일을 조립했다는 사실만으로 서버가 그 요청을 수락했다고 간주하지 않는다.

## 4. 기대값과 응답 채점

`expected.answers`의 boolean은 **의미 정답**이다. 실제 Predicate 응답은 `{"type":"predicate","name":"...","probability":0.0}` 형태의 확률이며 boolean이나 Jev의 `noul` 필드가 아니다. Choice 응답은 `choice`, `probabilities`, `confidence`를 반환한다. 각 답은 `name`으로 대응하고 예상 질문 10개의 중복·누락·형식·선택지·수치 범위를 검사한다. 예시 확률은 실측값이나 수용 임계값이 아니다.

- `expected.answers`에 없는 키는 **미채점**이다. 거짓이나 확률 0으로 채우지 않는다.
- 질문별 `type: "refusal"`, 누락·중복·알 수 없는 선택지·잘못된 형식·범위 밖 또는 비유한 수치, 호출 오류·시간 초과는 별도 기록하고 직접 처리를 허용하지 않는다. 다른 질문이 맞더라도 필요한 답이 없으면 완전한 통과로 세지 않는다.
- Predicate의 참·거짓·보류 경계와 Choice 수용 기준은 조정용 자료로 정한 뒤 평가 전에 고정한다. 이 자료에는 운영용 숫자 임계값을 넣지 않았다. 0.5를 무조건 운영 기준으로 쓰거나 Jev의 임계값을 복사하지 않는다.
- 임계값을 정하기 전에는 Choice의 의미 정답 일치, Predicate의 원래 확률과 Brier 점수 등으로 탐색할 수 있다. 이때 유효 응답 수·정답이 있는 문항 수·거절·오류·미채점 수를 함께 보고하고 직접 처리 합격률로 포장하지 않는다.
- `expected.decision`은 의미상 기대 경로다. `must_preserve_requests`는 A0 인계·최종 처리에서 보존할 요청을 사람이 확인하기 위한 기준이며 모델 입력이 아니다.

직접 처리 후보는 두 Choice가 각각 `draft_selected_thread`, `selected_thread`이고, `reply_draft_requested`는 참, 나머지 Predicate 7개는 거짓으로 각 수용 기준을 충족해야 한다. Spring의 권한·필수 입력·최신 상태 검사도 필요하다. 충돌·미확인·범위 밖 요청은 허용된 원문·문맥을 A0로 전달한다. `plan_with_a0`는 요청 전체 거절이 아니다.

## 5. 시나리오별 확인 지점

| 평가 후보 | 확인할 경계 |
| --- | --- |
| 01~02, 05~07, 09~10, 12, 14, 16 | 단일 초안, 광고 언급과 조회의 차이, 부정·인용·제목 속 지시 |
| 03~04, 08, 11, 13, 15, 17~18, 20, 30~33, 38 | 검색·발송·규칙·수신 변경·요약·복수 초안 등 복합 요청 누락 |
| 19, 21~29, 39~40 | 다른 대상, 기존 초안 편집, 새 메일, 모호함, 취소·정정·짧은 후속 요청 |
| 34~37 | 인사, 구독 재개, 규칙 중지, 발신자 표시의 가짜 지시 |
| 41~48 | 선택 없음·권한 실패·오래된 선택·버튼·기존 확인 절차·입력 부족과 검사 우선순위 |

특히 03·04·11·38처럼 초안 조건에 다른 요청이 섞인 사례는 **높은 confidence로 잘못 직접 처리한 경우**를 별도로 센다. 질문들이 서로 일치하면서 함께 틀린 결과도 포함한다. Choice 선택지 순서 변경은 별도 변형 시험으로 구분하고 원래 순서의 결과와 섞지 않는다.

## 6. 평가 기록과 통과 판단

| 구분 | 남길 내용 |
| --- | --- |
| 재현 조건 | 사례·질문 파일의 버전과 해시, 실제 모델·엔드포인트, 질문 순서, 선택한 임계값·평가 시각·실행 위치·동시 호출 조건 |
| 질문 결과 | 원래 응답·확률·confidence, 정답이 있는 항목의 오류, 거절·누락·형식 오류·미채점 수 |
| 경로 결과 | 의미상 기대 경로, 서버 실제 경로, 직접 통과·A0 복귀·보류 사유 |
| 요청 누락 | 실제 직접 통과 요청 중 필요한 요청을 누락한 비율과 원래 직접 처리 대상이 아닌 요청을 잘못 통과시킨 비율. 분모·건수 각각 표기 |
| 불필요한 복귀 | 직접 처리 가능한 의미 정답 사례 중 불필요하게 A0로 복귀한 비율. 오류·거절에 따른 복귀도 사유별 표기 |
| 지연·실패 | API 구간 p50·p95와 전체 업무 완료 시간, 오류·시간 초과·재시도. 실패한 요청을 지연·실패 보고에서 제거하지 않음 |
| 사용량·비용 | 제공사 `usage`, 정상 단가 기준 비용·크레딧 차감액·추가 현금 지출, A0 복귀·후속 역할·재시도 비용 |

서버 전용 사례는 모델 정확도의 분모에서 제외한다. 질문별 정확도와 10개 답을 결합한 경로의 품질을 구분하며, 전부 A0로 돌리는 구성도 유리해 보이지 않도록 직접 처리율과 불필요한 복귀를 함께 보고한다. 분류 재현율 98%·정밀도 90%를 라우팅 목표로 치환하지 않는다. 라우팅 수용 수치·표본·임계값·예산은 기존 후속 결정 대상이다.

이 자료만으로 초기 운영을 활성화하지 않는다. 기존 품질·안전·전체 지연·비용 기준과 사전에 정한 라우팅 수용 기준을 실제로 통과한 범위에만 적용한다. 합성 기대값·오프라인 파일 검사를 모델 실행 결과로 기록하지 않는다.
