## 2. Java 25와 21 비교

### 2.1 프로젝트에 도움이 되는 차이

비교 대상은 무료 OpenJDK 배포판인 Eclipse Temurin의 21 LTS와 25 LTS다. **신규 프로젝트에는 25 LTS를 추천**한다. 외부 메일·DB 통신이 많은 구조에서 가상 스레드 개선을 활용할 여지가 있고, 지원 기간도 더 길다. AI 모델의 추론 속도나 우리 서비스의 처리량이 특정 비율로 개선됐다는 실측 근거는 없다.

| 비교 | Java 21 | Java 25 | Uteum-Mail에서의 의미 |
| --- | --- | --- | --- |
| 가상 스레드 | 이미 정식 지원. `synchronized` 안에서 대기할 때 실행용 OS 스레드가 묶일 수 있음 | JDK 24의 JEP 491 개선 포함. 해당 잠금 때문에 OS 스레드가 묶이는 문제를 해소 | 동기식 메일·HTTP·DB I/O를 가상 스레드로 처리할 때 유리할 수 있음. 실제 사용 경로·라이브러리·부하에 따라 효과가 다름 |
| 메모리 최적화 | 일반적인 객체 헤더 사용 | 작은 객체 헤더가 정식 옵션으로 제공됨 | 객체가 많은 서버에서 메모리를 줄일 여지. 25에서도 기본 활성화가 아니며 `-XX:+UseCompactObjectHeaders` 적용 전후 측정 필요 |
| 시작과 워밍업 | 기존 클래스 공유·JIT 기능 사용 | AOT 캐시와 메서드 프로파일 재사용 개선 포함 | 서버 재시작·증설 후 준비 시간을 줄일 여지. 사전 실행으로 캐시를 만드는 절차가 필요하며 개별 요청의 지연 개선을 보장하지 않음 |
| 실행 문맥 | ThreadLocal 등 사용 | ScopedValue 정식 제공 | 불변 문맥 전달에 활용 가능. 기존 Spring 인증·트랜잭션 문맥이 자동 대체되는 것은 아님 |
| Temurin 제공 기간 | 최소 2029년 12월까지 | 최소 2031년 9월까지 | 새 프로젝트의 다음 큰 버전 전환을 늦출 수 있음. JDK 지원과 Spring 지원 기간은 별도 |

가상 스레드는 Java 21에서도 사용할 수 있다. Java 25에서도 네이티브 코드와 관련된 일부 고정 상황은 남으며, DB 커넥션 수와 메일 제공사의 호출 한도는 별도로 제한해야 한다. [OpenJDK JEP 491](https://openjdk.org/jeps/491), [JEP 519](https://openjdk.org/jeps/519), [JEP 515](https://openjdk.org/jeps/515), [JDK 25 변경 사항](https://docs.oracle.com/en/java/javase/25/migrate/significant-changes-jdk-25.html), [Temurin 지원 기간](https://adoptium.net/support/)

### 2.2 Java 25를 선택할 때의 부담

| 항목 | 판단과 대응 |
| --- | --- |
| 도구·라이브러리 호환 | 오래된 빌드 플러그인·바이트코드 처리 도구·테스트 도구·APM 에이전트가 Java 25를 지원하는지 확인해야 한다. 사용 제품에서 문제가 재현되면 21이 더 간단한 선택일 수 있다. |
| 실행 환경 일치 | Java 25 대상으로 빌드한 결과물은 Java 21에서 실행할 수 없다. 개발·CI·컨테이너의 JDK를 맞춘다. 21 대상으로 빌드할 수 있지만 25 전용 API·문법 사용에 제약이 생긴다. |
| 최적화 운영 | AOT 캐시·객체 헤더 옵션을 도입하면 빌드·관찰 조건이 추가된다. 첫 구현은 기본 JVM 설정으로 시작하고 측정된 병목이 있을 때 적용하는 안을 추천한다. |
| 실제 성능 | 25가 모든 요청에서 빠르거나 메모리를 덜 쓰는 것은 아니다. 동일 데이터·DB·JVM 자원으로 목록·동기화·배치 성능을 확인해야 한다. |
| Preview 기능 | 25 LTS에도 Preview·Incubator 기능이 포함된다. 초기 운영 코드에서 이 기능에 의존하지 않는 안을 추천한다. |

Spring Boot 공식 문서의 4.1.1은 Java 17~26을 지원하므로 21과 25 모두 프레임워크 요구 범위에 든다. Gradle 자체를 Java 25로 실행하려면 9.1.0 이상이 필요하다. Spring 지원 범위만 확인하고 빌드 플러그인·메일 라이브러리까지 호환된다고 판단하지 않는다. [Spring Boot 요구사항](https://docs.spring.io/spring-boot/system-requirements.html), [Gradle Java 호환표](https://docs.gradle.org/current/userguide/compatibility.html)

**사용자 확정(2026-10-01):** Temurin Java 25 LTS와 Spring Boot 4.1.x를 사용한다. Java 빌드 도구·메일 라이브러리·DB 드라이버·테스트·APM, Boot의 지원 범위와 필수 플러그인을 함께 확인한다. 필수 의존성의 Java 25 호환 문제가 확인되면 Java 21 LTS로 전환하는 대응도 승인됐다. 재현 근거와 전환 결과를 기록하고 개발·CI·배포 환경을 함께 맞춘다. 현재는 의존성 조합과 실행 코드가 없어 빌드·연동 검증 완료를 뜻하지 않는다.

## 3. SQS 예상 비용

### 3.1 계산 기준

서울 리전 `ap-northeast-2`, SQS Standard의 첫 요금 구간은 **100만 요청당 $0.40**다. 매월 첫 100만 요청 무료분은 여러 리전 사용량을 합산하며 큐마다 별도로 생기지 않는다. FIFO는 같은 구간에서 100만 요청당 $0.50이며, Standard의 Fair Queue 기능은 해당 요청에 추가 요금이 붙는다. 아래 표는 일반 Standard만 계산한다. [AWS 서울 SQS 공개 가격표](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AWSQueueService/current/ap-northeast-2/index.json), [SQS 과금 규칙](https://aws.amazon.com/sqs/pricing/)

**작업 1건과 유료 요청 1회는 다르다.** 예시에서는 작은 메시지를 묶음 없이 보내기 1회·받기 1회·완료 후 삭제 1회로 처리해 작업당 3회로 잡았다. 메시지 본문은 작업 ID·대상 ID 등으로 작게 유지한다.

| 월 작업 수 | 예시 요청 수 | 무료분 적용 후 SQS 요청 요금 |
| --- | --- | --- |
| 10만 건 | 30만 회 | $0.00 |
| 100만 건 | 300만 회 | $0.80 |
| 1,000만 건 | 3,000만 회 | $11.60 |
| 1억 건 | 3억 회 | $119.60 |

계산식: `max(요청 수 - 1,000,000, 0) × 0.40 / 1,000,000`. 다른 서비스가 무료분을 소진하지 않았다는 가정이다. 무료분 없이 월 100만 작업·300만 요청이면 $1.20이다. 사용량 예시는 예상 고객 수나 실제 처리량을 뜻하지 않는다.

### 3.2 실제 비용을 바꾸는 요소

- 빈 큐 확인, 재시도, 처리 중 메시지 숨김 시간 연장, 실패 큐 처리도 요청을 만든다. 긴 대기 방식인 long polling과 묶음 처리를 검토한다.
- 메시지 크기는 64KB 단위로 요청량에 반영된다. 원본 메일·첨부 전체를 큐에 넣는 방식은 피하는 안을 추천한다.
- 메일 한 건이 동기화·분류·재분석 등 여러 작업을 만들 수 있다. 비용은 메일 수보다 실제 큐 요청량으로 계산한다.
- 위 금액에는 AI 호출·워커 서버·KMS·NAT Gateway·VPC 엔드포인트·리전 간 통신·세금이 포함되지 않는다. 같은 리전의 SQS 데이터 전송 자체가 무료여도 별도 네트워크 장비 요금까지 없어지지는 않는다.

**사용자 확정(2026-10-01):** 초기부터 SQS Standard를 사용한다. 이 예시에서 요청 요금은 작고 큐 서버의 패치·복구를 직접 운영할 필요를 줄인다. 작업의 최종 상태는 Spring이 PostgreSQL에 관리하고 outbox를 통해 작업 ID를 발행하는 기준을 채택한다. SQS는 중복 전달 가능성이 있어 작업 ID와 결과 중복 방지가 필요하다. 완료 후 삭제·숨김 시간 연장·재시도의 세부 값은 구현 설계에서 구체화한다. [SQS Standard 동작](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html)

### 3.3 큐를 만들어 두고 사용하지 않을 때

**SQS에는 빈 큐를 보유하는 고정 요금이나 최소 사용료가 없다.** 생성·설정 과정의 소수 API 요청 이후 호출이 없으면 지속적인 SQS 요청 요금도 발생하지 않는다. 다만 사용자가 없어도 워커·관리 도구가 큐를 확인하면 요청 수에 포함된다. 연결해 둔 시험용 메일 계정의 동기화·분석도 실제 사용량이다. [SQS 과금 규칙](https://aws.amazon.com/sqs/pricing/)

다음은 서울 리전 Standard, 월 730시간, 빈 큐, 다른 SQS 사용량 없음, 매월 100만 요청 무료분 적용이라는 가정의 계산이다. 폴링 루프 수는 서버 수가 아니라 동시에 큐 수신을 기다리는 호출 수를 뜻한다.

| 실행 상태 | 월 수신 요청 수 | 월 SQS 요청 요금 |
| --- | --- | --- |
| 빈 큐만 보유하고 호출하지 않음 | 0회 | $0 |
| 수신 루프 1개, 20초 long polling | 약 131,400회 | $0 |
| 수신 루프 10개, 각각 20초 long polling | 약 1,314,000회 | 약 $0.13 |
| 수신 루프 1개, 1초마다 짧은 조회 | 약 2,628,000회 | 약 $0.65 |

20초 long polling의 계산은 `730 × 3,600 ÷ 20`이다. 메시지가 도착하면 기다리던 요청이 일찍 반환되므로, 매 작업을 무조건 20초 지연시키는 방식이 아니다. 실제 작업이 있으면 보내기·삭제·재시도 요청을 함께 더한다. [SQS long polling](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-short-and-long-polling.html)

SQS 요청 요금과 워커를 실행하는 서버 비용은 별도다. NAT Gateway·VPC 엔드포인트 같은 유료 네트워크 구성을 추가하면 큐 요청이 적어도 별도 비용이 생길 수 있으므로 초기 배포 견적에 포함한다. SQS 사용만을 이유로 이런 장비를 모두 도입할 필요는 없다. [NAT Gateway 요금](https://aws.amazon.com/vpc/pricing/)

### 3.4 추가 큐 요금을 줄이는 대안과 유지보수

| 방식 | 추가 비용 조건 | 개발·유지보수 부담 | 나중에 SQS로 전환할 때 |
| --- | --- | --- | --- |
| SQS Standard부터 사용 | 사용량이 무료 범위에 들면 요청 요금 $0. 워커·네트워크는 별도 | 큐 서버의 패치·복구 부담을 줄임. 작업 상태·중복 방지·권한 검증은 애플리케이션이 구현 | 제품 교체 없이 같은 큐를 사용하며 워커·처리량을 조정 가능 |
| 기존 PostgreSQL의 작업 테이블 | 별도 큐 서비스료 없음. DB·워커 자원은 사용 | 작업 선점, 임대 만료, 재시도 시점·횟수, 실패 작업 확인, 인덱스·정리·폴링 부하를 관리 | 전달 경로를 추가하고 미완료 작업의 이관·중복·재시작을 시험해야 함 |
| 자체 RabbitMQ 등 별도 브로커 | 소프트웨어 요금 외 서버·디스크·운영 비용 고려 | 별도 프로세스·영속 저장·업데이트·장애 복구를 운영 | 클라이언트·전달 방식·장애 계약 변경을 검증 |
| 메모리 큐·단순 HTTP 호출 | 별도 큐 서비스료 없음 | 영구 작업 기록이 없으면 재시작·통신 장애 때 작업을 복구할 수 없음 | 운영에 필요한 내구성을 별도로 구현해야 함 |

PostgreSQL의 `SKIP LOCKED`는 여러 소비자가 큐 형태의 테이블을 조회할 때 잠금 경합을 줄이는 데 사용할 수 있다. 이것만으로 작업 큐 전체가 완성되는 것은 아니다. AI 실행 내내 DB 트랜잭션·행 잠금을 유지하지 않고 짧은 선점과 저장된 임대·상태를 사용하는 상세 설계가 필요하다. [PostgreSQL 잠금 절](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

**판단:** 초기 비용 절감만이 목적이라면 SQS를 자체 큐로 대체하는 이득은 작다. 자체 큐가 절약하는 월 요금보다 구현·복구 시험·나중의 전환 작업이 커질 수 있다. AWS 의존성을 피하거나 이미 검증된 DB 작업 처리 기반이 있을 때 PostgreSQL 큐를 대안으로 선택할 수 있다. 실제 코드가 없는 현재 단계에서 필요한 일수를 단정하지 않는다.

어느 방식을 택해도 작업 ID·상태·결과 검증은 공통으로 필요하다. 전달 부분을 업무 처리와 구분하면 추후 교체 범위를 줄일 수 있지만, 설정 한 줄로 안전하게 전환된다고 가정하지 않는다.

## 4. RDS 필요성과 예상 비용

### 4.1 RDS는 필수인가

PostgreSQL은 로컬 Docker·일반 서버·다른 관리형 DB에서도 실행할 수 있다. Spring·FastAPI를 선택했다고 RDS가 필요한 것은 아니다. RDS를 선택하는 이유는 백업·시점 복구·유지보수 같은 운영 작업을 서비스에 맡기기 위해서다. 쿼리·인덱스·권한·용량·복원 확인은 RDS에서도 프로젝트 책임으로 남는다. [RDS 자동 백업](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)

일반 RDS DB 인스턴스는 **사용자나 쿼리가 없어도 실행 시간과 저장공간에 따라 과금**된다. 일시 중지하면 인스턴스 시간 요금은 멈추지만 저장공간·적용되는 백업 등의 비용은 남고, 최대 7일 뒤 자동으로 다시 시작한다. 상시 서비스용 RDS를 만들어 중지해 두는 방식은 영구적인 무료 대안이 아니다. [RDS 일시 중지와 과금](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_StopInstance.html)

| 운영 방법 | 비용과 장점 | 맡아야 할 작업·제약 |
| --- | --- | --- |
| 개발 PC의 PostgreSQL | 별도 클라우드 DB 요금 없이 개발·연동 시험 가능 | 사용자 대상 상시 서비스의 호스팅으로 쓰기에는 가용성 제약 |
| 서버에 직접 설치 | 기존 서버 여유 자원을 쓰면 현금 지출을 낮출 수 있음 | OS·DB 업데이트, 외부 백업, 복원, 디스크·장애 대응을 직접 운영. 별도 VM을 쓰면 절감액을 다시 계산해야 함 |
| RDS Single-AZ | 관리 기능을 사용하며 아래의 고정 기본 비용으로 시작 가능 | 대기 DB가 있는 자동 장애 전환 구성이 아님. DB·애플리케이션의 용량 검증 필요 |
| RDS Multi-AZ | 다른 AZ의 대기 DB로 장애 전환 가능 | 비용이 증가하므로 고도화 시 재검토 |

서버 하나에 Spring·Python·PostgreSQL을 모두 배치하면 비용은 줄일 수 있으나 서버 장애·메모리 부족·디스크 문제가 같이 영향을 준다. 컨테이너 분리만으로 이 위험이 사라지지는 않는다. 직접 운영을 선택한다면 서버 밖의 백업과 실제 복원 절차를 초기 운영 범위에 포함하는 안을 추천한다.

### 4.3 사용자가 없는 초기 단계의 DB 대안

2026-10-01 사용자가 PostgreSQL 18.x를 검증 기준으로 한 로컬 개발과 공유 데모·소규모 비공개 베타의 무료 관리형 DB 우선 비교를 승인했다. 수요·운영 부담이 커지면 기존 호스팅의 유료 확장과 RDS 이전을 비교한다. 초기 DB 사업자·요금제와 전환 시점은 미확정이다.

| 대안 | 별도 DB 서비스 요금 | 우리 서비스에서 확인할 한계 | 판단 |
| --- | --- | --- | --- |
| 로컬 PostgreSQL | 기존 개발 PC에서 사용하면 추가 클라우드 DB 요금 $0 | PC 가동·네트워크에 의존. 장비·전기 비용까지 없다는 뜻은 아님 | 개발·개인 연동 시험의 첫 선택으로 추천 |
| Neon Free | 무료 한도 안에서 $0. 프로젝트당 저장공간 0.5GB·월 100 CU-hours | 5분 비활동 후 compute가 멈춤. 재접속 지연·연산 한도·백업 범위 확인 | 간헐적인 공유 개발·데모 후보 |
| Supabase Free | 무료 한도 안에서 $0. DB 500MB | 공유 CPU·500MB RAM, 1주 비활동 시 일시 정지. 별도 데이터 내보내기·외부 백업 준비 | 소규모 공유 개발·데모 후보 |
| 기존 VM에서 PostgreSQL 직접 운영 | 추가 DB 서비스료 없음. VM·디스크·백업 비용은 별도 | 서버 자원 공유, DB·OS 패치, 백업·복구·공간 관리를 직접 담당 | 이미 VM을 운영하고 관리 책임을 맡을 수 있을 때 비교 |

무료 한도는 사용자 수보다 데이터·연산·전송량에 좌우된다. 메일 메타데이터·인덱스·벡터도 DB 공간을 사용하므로 적은 사용자라도 한도를 넘을 수 있다. 실제 사용자에게 제공할 때는 휴면·복구·성능 조건을 먼저 시험한다. [Neon 공식 요금제 문서](https://github.com/neondatabase/website/blob/main/content/docs/introduction/plans.md), [Supabase 요금제](https://supabase.com/pricing), [Supabase 무료 프로젝트 백업 안내](https://supabase.com/docs/guides/platform/backups)

**설계상 주의:** 자동 휴면 DB를 작업 테이블 폴링·연결 확인·메일 동기화가 계속 조회하면 비활동 시간이 생기지 않을 수 있다. 예를 들어 0.25 CU로 월 730시간을 계속 가동하면 182.5 CU-hours가 되어 Neon Free의 월 100 CU-hours를 넘는다. 이는 가정 계산이며 실제 계정 사용량을 측정한 값이 아니다. SQS를 기다리는 동안에는 불필요한 DB 조회를 줄일 수 있지만 다른 주기 작업도 함께 확인해야 한다.

### 4.4 채택한 진행 방향과 전환 부담

1. **개발·수요 없음:** 로컬 PostgreSQL 18.x와 SQS Standard를 기준으로 진행한다. 개발하지 않는 동안 불필요한 워커 호출을 줄인다.
2. **공유 데모·아주 작은 비공개 베타:** 무료 관리형 PostgreSQL을 우선 비교한다. 저장·연산 한도와 휴면·백업 조건을 확인하고, 실제 사용자 베타 전에는 승인된 복구 목표의 충족 여부를 시험한다. 무료 구성이 목표를 충족하지 못하면 유료 관리형 또는 직접 운영의 총비용을 다시 제시한다.
3. **반복 사용·실제 수요 확인:** 기존 사업자의 유료 확장과 RDS 이전의 총비용을 비교한다. 데이터 한도, 연결·검색 부하, 복구 요구 또는 유지보수 부담이 커지면 사용자 수가 많아지기 전이라도 재검토한다.
4. **고도화:** RDS가 적합하다고 판단되면 당시 부하와 예산으로 크기를 정한다. ECS·Multi-AZ·복제본은 각각 필요성을 확인해 선택한다.

작은 PostgreSQL DB를 예정된 쓰기 중단 시간에 옮기는 것은 일반적인 이전 방식이다. PostgreSQL의 덤프·복원 도구를 이용할 수 있으며, 같은 엔진·지원되는 확장·일반적인 스키마를 유지하면 변경 범위를 줄일 수 있다. 데이터가 커지거나 무중단 이전이 필요하거나 특정 사업자의 인증·저장소 기능까지 깊이 사용하면 이전 부담이 커진다. [PostgreSQL 덤프·복원](https://www.postgresql.org/docs/current/backup-dump.html), [RDS PostgreSQL 가져오기](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Procedural.Importing.html)

**유지보수 판단:** 직접 운영은 초기에 저렴할 수 있지만 백업 자동화·패치·복원 연습이 반복 업무가 된다. 이 업무가 기능 개발을 지연시키면 관리형 DB 비용을 지불하는 편이 나을 수 있다. 무료 관리형 DB를 먼저 검증하고 유료 전환 또는 RDS 이전을 비교하는 방향은 채택했으며, 구체적 사업자는 선택 전이다.

전환 때는 API뿐 아니라 메일 동기화·AI 결과 저장의 쓰기도 정리하고, 데이터·권한·확장·미완료 작업을 검증한다. 연결 주소만 바꾸는 작업으로 취급하지 않는다. 상세 전환 절차와 재검토 조건은 [인프라 고도화 계획](09-인프라-고도화-계획-v1.0.md)을 따른다. 초기 호스팅 사업자·운영 예산·작업 계약의 남은 세부 선택은 [후속 결정 목록](10-후속-결정-목록-v1.0.md)에서 관리한다.
