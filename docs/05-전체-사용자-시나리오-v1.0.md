# 통합 이메일 AI 비서 — 전체 사용자 시나리오 v1.0

- 작성일: 2026-09-28
- 범위: 현재 기획의 사용자 여정, 정상 처리, 예외·실패, 중단·복구, 후속 기능의 조건부 흐름
- 구성: **17개 영역 · 상세 시나리오 182개 · 통합 사용 흐름 10개**
- 기준: 기획서 v1.5, 에이전트 상세 설계 v0.3, 캘린더 연동 검토
- 용도: 화면 설계, 기능 범위 결정, 개발 요구사항·사용성 검증·인수 기준의 출발점
- 상태: 설계 문서. 사례는 가상이며 실제 구현·API·기기 테스트를 통과했다는 의미가 아님

## 1. 이 문서를 읽는 방법

‘전체’는 현재 기획에서 식별한 사용자 행동과 상태 전환을 전체 서비스 여정에 걸쳐 정리했다는 뜻이다. 계정·기기·권한·언어의 모든 조합을 중복 나열하지 않고, 기능별 사례와 공통 변형 조건을 함께 적용한다. 신규 기능이나 제공사 제약이 확인되면 해당 시나리오를 추가·수정한다.

사용자에게 보이는 비서는 하나다. 내부의 5개 에이전트는 기존 설계를 유지하며 이 문서에서 사용자에게 개별 에이전트를 선택하게 만들지 않는다. 메일·계정·서비스·날짜·금액 예시는 동작 설명용이며 실제 사용자 정보가 아니다.

| 표시 | 의미 | 상세 사례 수 |
| --- | --- | --- |
| 초기 핵심 설계 | 기획서 P0 목표 안에서 정의한 기대 동작. 출시·구현 완료 표시가 아님 | 131 |
| 후속 기능 검토 | 캘린더·첨부 AI 등 P1 또는 추가 검증이 필요한 기능 | 26 |
| 운영·화면 설계 제안 | 가입·세션·결제·접근성 등 사용에 필요한 보완안. 세부 정책 미확정 | 20 |
| 후순위·현재 범위 밖 | 상대별 말투·팀 기능·미지원 자동 실행 등에 대한 안내 흐름 | 5 |

각 사례는 **상황·요청 → 사용자와 앱의 흐름 → 예외·복구 → 완료 기준**으로 읽는다. ‘완료 기준’에는 정상 처리뿐 아니라 사용자가 미지원·미확정 상태와 다음 행동을 이해한 경우도 포함한다. 새 기능의 채택 여부와 외부 API의 지원 여부를 별도로 결정한다.

## 3. 처음부터 끝까지 보는 통합 사용 흐름

기능 목록보다 실제 사용 순서로 읽고 싶다면 이 절부터 확인한다. 아래 10개 흐름은 서로 다른 사용자이며, 모든 사용자가 모든 단계나 기능을 써야 한다는 뜻이 아니다.

### JRN-01. 광고 때문에 중요한 메일을 놓치는 일반 사용자

- **상황:** 네이버 메일만 사용하는 사용자가 처음 가입해 오래된 광고 구독을 정리한다.
- **사용 흐름:** 계정을 연결하고 통합함을 확인한다. 잘못 분류된 신청 결과를 중요하게 고친 뒤 향후 기준을 저장한다. 원하지 않는 쇼핑몰의 이메일 광고만 해제한다.
- **확인할 분기:** 조회·분류와 외부 수신 해제는 별개다. 필수 안내를 유지하고 해제 결과를 실제 상태로 확인한다.
- **상세 연결:** ONB-03 → CON-02 → CLS-01 → CLS-05 → RUL-02 → UNS-01

### JRN-02. 업무·개인 계정을 함께 쓰는 스타트업 구성원

- **상황:** 한 사람이 여러 업무 계정과 개인 계정을 사용하지만 동료 초대는 원하지 않는다.
- **사용 흐름:** 계정을 각각 연결하고 개인 자료의 교차 사용을 제한한다. 업무용 중요 기준을 저장한 뒤 관련 자료를 검색하고 허용된 업무 계정 자료로 답장을 작성·확인 발송한다.
- **확인할 분기:** 개인 가입을 팀 도입으로 확대하지 않는다. 통합 조회와 초안의 자료 사용 범위는 다르다.
- **상세 연결:** CON-05 → ONB-05 → RUL-04 → AST-01 → DRF-04 → SND-01

### JRN-03. 한 메일에 여러 요청을 받은 프리랜서

- **상황:** 견적 발송과 소개 자료 수정 요청을 함께 받았다.
- **사용 흐름:** 두 업무 후보를 확인하고 후속 요구사항 메일을 연결한다. 가격을 입력해 견적 답장을 보낸 뒤 견적 업무만 완료한다. 소개 자료 수정과 상대 검토 대기는 각각 유지한다.
- **확인할 분기:** 메일 발송으로 모든 일이 완료되지 않는다. 기한 변경과 추가 요청은 기존 업무와의 관계를 확인한다.
- **상세 연결:** TSK-01 → TSK-02 → DRF-02 → SND-01 → TSK-08 → WAI-01

### JRN-04. 부분 답변을 놓치지 않고 후속 확인

- **상황:** 가격·납기 질문 중 가격만 답변을 받았다.
- **사용 흐름:** 납기 답변 대기를 남기고 확인할 날짜를 정한다. 알림을 보고 후속 초안을 작성해 확인 후 보낸다. 자료가 도착하면 내용 검토 뒤 업무 상태를 정한다.
- **확인할 분기:** 자동 응답과 형식적 확인을 실질적인 답으로 보지 않는다. 알림 시점과 상대 약속 날짜를 구분한다.
- **상세 연결:** WAI-03 → WAI-05 → WAI-07 → DRF-01 → SND-01 → WAI-04

### JRN-05. Google 없이 웹에서 Apple 캘린더 사용

- **상황:** 사용자는 네이버 메일과 iCloud 캘린더를 쓰며 우리 모바일 앱을 설치하지 않는다. 캘린더 기능 제공 후의 검토 시나리오다.
- **사용 흐름:** 메일을 연결하고 검증된 iCloud 직접 연결로 기본 캘린더를 고른다. 회의 후보를 확인해 등록하고 후속 변경 메일은 수정안으로 검토한다.
- **확인할 분기:** Google 계정은 요구하지 않는다. iCloud 연결 검증과 인증이 선행돼야 하며, 직접 수정한 일정과 충돌하면 비교한다.
- **상세 연결:** CON-02 → CAL-03 → CAL-04 → CAL-10 → CAL-13 → CAL-18

### JRN-06. Google 없이 Galaxy에서 일정 관리

- **상황:** 카카오메일과 삼성 계정 캘린더를 사용한다. Android 연결 모듈 제공 후의 검토 시나리오다.
- **사용 흐름:** Galaxy에서 실제 사용 가능한 캘린더를 연결한다. PC에서 일정을 승인하면 지정된 휴대전화가 처리하고 결과를 돌려준다. 재시도 때 기존 연결을 확인한다.
- **확인할 분기:** 휴대전화가 꺼져 있으면 반영 대기다. 웹만 제공하는 버전에서는 이 기기 연결 흐름이 가능하다고 안내하지 않는다.
- **상세 연결:** CON-04 → CAL-07 → CAL-10 → CAL-17 → CAL-20

### JRN-07. 잘못된 AI 판단을 고치고 다시 사용

- **상황:** 광고함에서 중요한 메일을 발견하고 기존 규칙에 문제가 있음을 알았다.
- **사용 흐름:** 해당 메일을 수정하고 판단 근거를 확인한다. 예외를 저장해 지정 기간만 재분류한다. 잘못된 규칙 변경은 영향 범위를 확인하고 되돌린다.
- **확인할 분기:** 일회성 수정과 지속 규칙을 구분한다. 재분류가 외부 수신 설정이나 이미 보낸 메일까지 되돌리지는 않는다.
- **상세 연결:** CLS-05 → AST-11 → RUL-03 → RUL-05 → RUL-09 → OPS-10

### JRN-08. 분석 범위를 줄이고 서비스 이용 종료

- **상황:** 개인 메일의 AI 분석을 중단한 뒤 장기적으로 우리 앱을 떠나려 한다.
- **사용 흐름:** AI 분석과 계정 참조 범위를 먼저 줄인다. 연결 해제·보관 데이터 삭제를 선택하고 독립 업무 처리 범위를 확인한다. 유료 상품이 있다면 갱신 중단과 계정 종료를 구분한다.
- **확인할 분기:** 외부 메일 계정 자체는 탈퇴하지 않는다. 백업·외부 처리 자료 등의 실제 삭제 상태와 남는 범위를 설명한다.
- **상세 연결:** DAT-01 → DAT-04 → DAT-08 → DAT-09 → PAY-06 → DAT-10

### JRN-09. 여러 광고 구독 해제 중 일부 실패

- **상황:** 일괄 해제 대상 중 일부는 성공하고 일부는 로그인이나 결과 확인이 필요하다.
- **사용 흐름:** 계정별 대상을 골라 묶음 해제를 요청한다. 항목별 결과를 확인하고 직접 설정 항목만 처리한다. 중단 요청 뒤에는 미실행 부분을 멈추고 결과가 불명확한 항목을 재확인한다.
- **확인할 분기:** 전부 성공했다고 뭉뚱그리지 않는다. 이미 요청된 외부 작업은 취소됐다고 가정하지 않는다.
- **상세 연결:** SVC-04 → UNS-04 → UNS-07 → UNS-08 → UNS-11 → SVC-05

### JRN-10. 잡담과 업무 요청을 오가며 계속 작업

- **상황:** 사용자가 답장 중 감사 인사와 범위 밖 질문을 섞고 다시 업무로 돌아온다.
- **사용 흐름:** 비서는 잡담에는 짧게 반응하고 지원 가능한 초안 작성은 진행한다. 모호한 항목만 확인하며 기존 작업을 보존한다. 복귀하면 새 답장 여부를 확인한 뒤 최종 발송을 검토한다.
- **확인할 분기:** 잡담을 규칙·장기 선호로 저장하지 않는다. 범위 밖 요청 때문에 전체 업무를 취소하지 않는다.
- **상세 연결:** AST-05 → AST-07 → AST-08 → AST-09 → DRF-09 → SND-01

## 4. 모든 시나리오에 공통으로 적용할 원칙

1. **자료의 출처를 표시한다.** 메일 원본 계정, 실제 발신 계정, 참고한 다른 계정, 서비스 상태 확인 출처·시각을 구분한다.
2. **명확한 지시를 반복 승인받지 않는다.** 규칙 저장과 정확한 범위의 마케팅 해제는 지시를 실행 근거로 삼는다. 일반 메일 발송과 초기 캘린더 변경은 정해진 최종 확인 흐름을 따른다. 모호한 대상·범위만 추가 확인한다.
3. **분류·수신 해제·차단·연결 해제·탈퇴를 구분한다.** 한 동작을 다른 동작으로 확대하지 않는다.
4. **업무·메일·일정의 상태를 분리한다.** 읽음·발송·달력 등록이 업무 완료를 자동 의미하지 않는다. 한 메일에 여러 업무, 여러 메일에 하나의 업무가 연결될 수 있다.
5. **실제 결과를 확인해 표시한다.** 준비·요청·처리 확인·미확정·실패·직접 설정 필요를 구분한다. 외부 요청 이후 중단·재시도도 실제 처리 상태부터 확인한다.
6. **권한과 설정을 마지막까지 확인한다.** 분석 제외·계정 참조 제한·연결 해제·데이터 삭제는 대기 작업과 늦은 결과에도 적용한다.
7. **범위 안의 되돌리기를 제공한다.** 분류 규칙과 내부 표시의 복구를 이미 전송한 메일·해제한 구독 등 외부 효과의 즉시 원복으로 설명하지 않는다.
8. **부분 성공을 보존한다.** 한 계정·항목의 실패가 독립적인 정상 기능을 막지 않게 하고, 묶음 결과는 항목별로 보여준다.
9. **지원 범위를 숨기지 않는다.** 웹 전용·네이티브 기기 연결·서버 API·수동 파일·읽기 전용 구독의 차이를 실제 제공 기능에 맞춰 안내한다.
10. **미확정 조건을 약속으로 바꾸지 않는다.** 가격·한도·보관 기간·지원 언어·기기·공급자 기능은 검증하고 확정한 값만 안내한다.

| 객체·처리 | 사용자에게 구분해 보여줄 상태 | 혼동하면 안 되는 것 |
| --- | --- | --- |

### ONB-01. 서비스 가입과 메일 연결 구분

범위: **운영·화면 설계 제안**

- **상황·요청:** 사용자가 네이버 메일만 쓰며 처음 방문한다.
- **사용 흐름:** 제공하는 가입 수단으로 우리 서비스 계정을 만든 뒤 메일 연결을 시작한다. 우리 서비스 로그인과 메일 접근 권한을 별도 단계로 설명한다.
- **예외·복구:** 가입 수단은 미확정이며 Google 가입만 강제하는 흐름을 기본으로 정하지 않는다. 실패 시 입력 상태와 재시도 경로를 제공한다.
- **완료 기준:** 사용자가 우리 서비스 계정과 연결한 메일 계정을 구분한다.

<a id="onb-02"></a>

### ONB-02. 가상 데이터로 먼저 체험

범위: **운영·화면 설계 제안**

- **상황·요청:** 실제 메일을 연결하기 전에 기능을 보고 싶다.
- **사용 흐름:** 가상 메일로 중요 분류·업무 후보·수신 관리의 예시를 보여준다.
- **예외·복구:** 데모임을 표시하고 실제 발송·마케팅 변경을 실행하지 않는다. 체험 종료 후 연결 화면으로 이동한다.
- **완료 기준:** 가상 자료가 실제 사용자 메일함이나 업무로 섞이지 않는다.

<a id="onb-03"></a>

### ONB-03. 메일 계정 하나로 시작

범위: **초기 핵심 설계**

- **상황·요청:** 사용자가 카카오메일 한 개만 연결하고 싶다.
- **사용 흐름:** 4종 중 해당 제공사를 고르게 하고 그 계정의 연결 절차만 진행한다.
- **예외·복구:** 여러 계정이나 팀 초대를 필수 조건으로 두지 않는다. 제공사 기능이 미검증이면 실제 지원 범위를 표시한다.
- **완료 기준:** 한 계정만으로 통합함과 허용된 기능을 사용한다.

<a id="onb-04"></a>

### ONB-04. 처음 분석할 기간과 범위 선택

범위: **초기 핵심 설계**

- **상황·요청:** 과거 전체 메일을 처음부터 분석하고 싶지 않다.
- **사용 흐름:** 받은·보낸 메일, 분석 기간, 외부 AI 처리 범위를 설명하고 사용자가 정하게 한다. 최근 30일은 제안값으로 표시한다.
- **예외·복구:** 분석 기간을 보관 기간이나 전체 가입 이력 조사 기간으로 설명하지 않는다. 분석을 거절해도 가능한 일반 조회 경로를 제공한다.
- **완료 기준:** 선택한 범위만 분석하며 기간 밖 자료를 분석했다고 표시하지 않는다.

<a id="onb-05"></a>

### ONB-05. 개인용·업무용 계정 구분

범위: **초기 핵심 설계**

- **상황·요청:** Gmail은 업무용, 네이버는 개인용으로 사용한다.
- **사용 흐름:** 계정에 알아보기 쉬운 이름을 붙이고 다른 계정 자료 참조 허용 범위를 설정한다.
- **예외·복구:** 같은 사용자 계정이라는 이유만으로 자료 교차 사용을 허용하지 않는다. 상세 설정 UI는 설계 제안이다.
- **완료 기준:** 통합 목록과 답장에 사용할 자료 범위가 구분된다.

<a id="onb-06"></a>

### ONB-06. 중요 기준을 대화로 설정

범위: **초기 핵심 설계**

- **상황·요청:** “거래처 견적과 지원사업 결과는 중요해.”라고 말한다.
- **사용 흐름:** 비서가 현재 대상 계정과 기준을 정리하고 명확한 범위의 규칙을 저장한다.
- **예외·복구:** 대상이 모호하면 필요한 부분만 확인한다. 예시 메일을 실제 수신 메일로 만들어내지 않는다.
- **완료 기준:** 사용자가 저장된 조건·범위와 수정 방법을 볼 수 있다.

<a id="onb-07"></a>

### ONB-07. 서비스 연동을 나중에 설정

- **예외·복구:** 목록 완성을 요구하며 메일 열람을 막지 않는다. 건너뛴 서비스를 확인 완료로 표시하지 않는다.
- **완료 기준:** 핵심 메일 기능을 쓰면서 서비스 연동을 나중에 이어갈 수 있다.

### ONB-08. 캘린더 선택을 건너뛰기

범위: **후속 기능 검토**

- **상황·요청:** 일정 연동을 아직 사용하지 않으려 한다.
- **사용 흐름:** Google·Apple·Samsung 선택과 ‘나중에 설정’을 제공한다.
- **예외·복구:** 선택하지 않았다는 이유로 메일·업무 기능을 막거나 임의 캘린더를 연결하지 않는다.
- **완료 기준:** 캘린더 연결 없이도 메일과 할 일을 관리한다.

<a id="onb-09"></a>

### ONB-09. 중단한 초기 설정 이어가기

범위: **운영·화면 설계 제안**

- **상황·요청:** 인증 중 창을 닫거나 모바일에서 연결을 끝내지 못했다.
- **사용 흐름:** 재로그인하면 완료한 단계와 남은 설정을 보여준다.
- **예외·복구:** 완료되지 않은 인증은 미연결로 남기고 민감한 입력값을 화면에 복구하지 않는다.
- **완료 기준:** 성공한 연결을 중복 생성하지 않고 남은 단계부터 이어간다.

<a id="onb-10"></a>

### ONB-10. 로그아웃·세션 만료 후 복귀

범위: **운영·화면 설계 제안**

- **사용 흐름:** 화면 접근과 변경 요청에 재인증을 요구하고 로그인 후 저장된 작업을 다시 읽는다.
- **예외·복구:** 미저장 초안의 복구 범위는 별도 정책으로 안내한다. 오래된 화면의 발송 버튼을 그대로 실행하지 않는다.
- **완료 기준:** 다른 사람이 이전 사용자의 메일을 열지 못하고 복귀 후 최신 상태로 작업한다.

### CON-08. 인증 만료·앱 비밀번호 변경

- **예외·복구:** 기존 메일이 보인다는 이유로 새 메일 수신이 정상이라고 표시하지 않는다.

### CON-09. 최초 동기화가 오래 걸림

- **상황·요청:** 메일이 많은 계정을 처음 연결했다.
- **사용 흐름:** 가져온 범위·남은 작업·AI 분석 상태를 구분해 보여주고 준비된 메일부터 열람하게 한다.
- **예외·복구:** 완료하지 않은 범위의 검색·중요 메일 개수를 전체 결과로 표시하지 않는다.
- **완료 기준:** 사용자는 무엇을 확인할 수 있고 무엇이 진행 중인지 안다.

<a id="con-10"></a>

### CON-10. 원래 메일 앱에서 보낸 답장 반영

범위: **초기 핵심 설계**

- **상황·요청:** 사용자가 네이버 앱에서 직접 회신했다.
- **사용 흐름:** 보낸 메일 변경을 가져와 관련 대화·업무에 연결하고 남은 행동을 재검토한다.
- **예외·복구:** 수신함만 읽고 “아직 답장하지 않았다”고 단정하지 않는다.
- **완료 기준:** 외부 앱에서의 회신을 보여주되 업무 완료는 별도로 판단한다.

<a id="con-11"></a>

### CON-11. 한 제공사만 장애·동기화 지연

범위: **초기 핵심 설계**

- **상황·요청:** Gmail은 정상이고 다음 메일만 갱신에 실패했다.
- **사용 흐름:** 계정별 상태와 확인 시각을 표시하고 정상 계정 사용은 계속한다.
- **예외·복구:** 지연된 계정의 “새 답변 없음”을 확정하지 않는다. 복구 후 해당 구간을 확인한다.
- **완료 기준:** 전체 앱 장애와 일부 계정 지연을 구분한다.

<a id="con-12"></a>

### CON-12. 재연결 뒤 중복·역순 변경 도착

범위: **초기 핵심 설계**

- **상황·요청:** 이미 처리한 메일이나 오래된 읽음 상태가 다시 들어온다.
- **사용 흐름:** 같은 원본 메시지는 갱신하고 최신 상태를 우선한다.
- **예외·복구:** 제목이 같다는 이유만으로 서로 다른 메일을 합치지 않는다. 연결이 불확실하면 별도 후보로 남긴다.
- **완료 기준:** 메일·업무·알림이 중복 생성되지 않고 최신 상태가 유지된다.

## 7. 통합 메일함·원문·첨부

기능 연결: F2, F7, F9 · 주요 화면: S2, S4, S6

<a id="inb-01"></a>

### INB-01. 여러 계정을 한 목록에서 확인

범위: **초기 핵심 설계**

- **상황·요청:** 아침에 계정별 사이트를 모두 열고 싶지 않다.
- **사용 흐름:** 통합함에서 원본 계정과 날짜를 함께 보고 계정·유형·중요도로 필터링한다.
- **예외·복구:** 한 계정이 끊겼으면 결과 범위에 표시한다. 중요·광고 보기를 서로 배타적인 원본 폴더로 오인시키지 않는다.
- **완료 기준:** 원하는 범위의 메일을 출처와 함께 확인한다.

<a id="inb-02"></a>

### INB-02. 메일 원문과 대화 순서 확인

범위: **초기 핵심 설계**

- **상황·요청:** 요약보다 원문과 이전 회신을 읽고 싶다.
- **사용 흐름:** 해당 메시지·대화를 열어 시간순 내용과 원본 계정을 표시한다.
- **예외·복구:** 제목·발신자가 비슷한 다른 거래를 자동 합치지 않는다. 긴 인용문과 최신 본문을 구분한다.
- **완료 기준:** 요약의 근거를 직접 확인할 수 있다.

<a id="inb-03"></a>

### INB-03. 읽음·안 읽음 변경

범위: **초기 핵심 설계**

- **상황·요청:** 읽은 메일을 나중에 다시 보려고 안 읽음으로 바꾼다.
- **사용 흐름:** 해당 메일의 상태를 변경하고 제공사 반영 상태를 표시한다.
- **예외·복구:** 동기화 실패 시 앱에서만 바뀐 상태를 서버 완료처럼 표시하지 않는다. 읽음 변경으로 할 일을 완료하지 않는다.
- **완료 기준:** 메일 읽음 상태와 업무 상태가 독립적이다.

<a id="inb-04"></a>

### INB-04. 첨부 열람·다운로드

범위: **초기 핵심 설계**

- **상황·요청:** 계약서나 이미지 첨부를 열어 본다.
- **사용 흐름:** 사용자 권한을 확인한 뒤 제공 가능한 미리보기 또는 다운로드를 제공한다.
- **예외·복구:** 암호화·손상·미지원 형식은 안내한다. 내려받을 수 있다는 이유로 AI가 내용을 읽었다고 표시하지 않는다.
- **완료 기준:** 파일을 확인하거나 열지 못한 이유를 알 수 있다.

<a id="inb-05"></a>

### INB-05. 첨부 누락·삭제된 파일

범위: **초기 핵심 설계**

- **상황·요청:** 메일에 첨부 언급은 있는데 파일이 없거나 조회되지 않는다.
- **사용 흐름:** 실제 첨부 목록을 확인하고 파일 없음·가져오기 실패를 구분한다.
- **예외·복구:** AI가 첨부 내용을 추정하거나 없는 파일을 답장에 자동 첨부하지 않는다.
- **완료 기준:** 사용자가 원문 확인·재요청 등 다음 행동을 선택한다.

<a id="inb-06"></a>

### INB-06. 원문이 삭제되거나 접근 불가

범위: **초기 핵심 설계**

- **상황·요청:** 이미 연결한 업무에서 원문을 열었지만 제공사에 메일이 없다.
- **사용 흐름:** 조회 불가와 남아 있는 업무·최소 근거 정보를 구분해 표시한다.
- **예외·복구:** 남아 있는 요약을 최신 원문으로 안내하지 않는다. 업무를 자동 완료·삭제하지 않는다.
- **완료 기준:** 사용자가 업무 유지·수정·제외를 선택한다.

<a id="inb-07"></a>

### INB-07. 빈 메일함·필터 결과 없음

범위: **초기 핵심 설계**

- **상황·요청:** 연결 직후 또는 강한 필터 때문에 목록이 비어 있다.
- **사용 흐름:** 실제 메일 없음, 동기화 중, 조건에 맞는 결과 없음의 이유를 구분한다.
- **예외·복구:** 분석 실패를 ‘중요 메일 없음’으로 바꾸지 않는다. 필터 해제·동기화 확인 경로를 제공한다.
- **완료 기준:** 빈 화면의 이유와 다음 행동이 명확하다.

<a id="inb-08"></a>

### INB-08. 모바일 웹에서 메일 확인

범위: **초기 핵심 설계**

- **상황·요청:** 작은 화면에서 통합함과 비서를 이용한다.
- **사용 흐름:** 목록에서 상세로 이동하고 돌아왔을 때 필터·읽던 위치를 유지하는 흐름을 제공한다.
- **예외·복구:** 모바일 웹을 설치형 앱의 기기 캘린더 권한과 동일하게 안내하지 않는다.
- **완료 기준:** 모바일에서도 출처·발신 계정과 핵심 버튼을 확인한다.

<a id="inb-09"></a>

### INB-09. 보관·삭제·차단을 요청

범위: **후속 기능 검토**

- **상황·요청:** “이 광고 메일들을 보관하거나 지워줘.”라고 한다.
- **사용 흐름:** 제공 중인 기능과 대상·범위를 확인하고 지원되는 명시적 동작만 제공한다.
- **예외·복구:** 현재 제품이 지원하지 않으면 원래 메일 서비스의 관리 경로를 안내한다. 분류 요청을 삭제로 바꾸지 않는다.
- **완료 기준:** 실제 지원한 동작과 결과를 표시하며 분류·구독 해제와 구분한다.

<a id="inb-10"></a>

### INB-10. 외부 이미지·링크 열기

범위: **운영·화면 설계 제안**

- **상황·요청:** 메일의 원격 이미지나 외부 사이트 링크를 열려고 한다.
- **사용 흐름:** 외부 콘텐츠 표시와 사이트 이동의 효과를 이해할 수 있게 하고 실제 출처를 보여주는 흐름을 설계한다.
- **예외·복구:** 단순 열람을 수신 해제·로그인·구매 등의 실행으로 처리하지 않는다. 추적 콘텐츠의 기본 로드 정책은 별도 확정한다.
- **완료 기준:** 사용자가 외부 이동을 인지하고 선택한다.

## 8. 메일 유형·중요도·오분류 수정

기능 연결: F3, F9, F10 · 주요 화면: S2, S4, S9

<a id="cls-01"></a>

### CLS-01. 일반 광고 분류

범위: **초기 핵심 설계**

- **상황·요청:** 오래전 가입한 쇼핑몰의 할인 메일이 도착한다.
- **사용 흐름:** 광고 유형으로 분류하고 전체 목록·검색에서 계속 찾을 수 있게 한다.
- **예외·복구:** 광고 분류만으로 수신 해제·발신자 차단·원본 삭제를 실행하지 않는다.
- **완료 기준:** 광고의 방해는 줄고 메일 접근은 유지된다.

<a id="cls-02"></a>

### CLS-02. 중요한 뉴스레터·할인 메일

범위: **초기 핵심 설계**

- **상황·요청:** 사용자가 구독한 업계 뉴스나 특정 할인 정보를 중요하게 지정했다.
- **사용 흐름:** 뉴스레터·광고 유형과 중요 표시를 함께 적용한다.
- **예외·복구:** 일반적인 광고 판단보다 사용자의 명시적 중요 기준을 우선한다.
- **완료 기준:** 중요한 광고가 광고라는 이유로 묻히지 않는다.

<a id="cls-03"></a>

### CLS-03. 광고와 주문·보안 안내가 섞인 발신자

범위: **초기 핵심 설계**

- **상황·요청:** 같은 주소에서 쿠폰과 결제 영수증이 번갈아 온다.
- **사용 흐름:** 메시지 내용별로 유형과 중요도를 판단하고 혼합 내용은 함께 표시한다.
- **예외·복구:** 발신자만 보고 결제·보안 안내를 광고와 같은 수준으로 숨기지 않는다.
- **완료 기준:** 거래·보안 정보를 별도로 확인한다.

<a id="cls-04"></a>

### CLS-04. 처음 보는 발신자의 중요한 메일

범위: **초기 핵심 설계**

- **상황·요청:** 처음 거래하는 업체의 계약 요청이 도착한다.
- **사용 흐름:** 알려진 발신자 여부 외에 내용·사용자 기준을 검토한다.
- **예외·복구:** 판단 근거가 부족하면 확인 필요로 남긴다. 기존 발신자 목록에 없다는 이유로 일반 처리하지 않는다.
- **완료 기준:** 새로운 중요한 메일을 발견하거나 검토할 기회를 제공한다.

<a id="cls-05"></a>

### CLS-05. 중요 메일을 광고로 잘못 분류

범위: **초기 핵심 설계**

- **상황·요청:** 사용자가 광고 보기에서 지원사업 결과 메일을 발견한다.
- **사용 흐름:** 유형·중요도를 수정하고 해당 메일을 즉시 다시 표시한다.
- **예외·복구:** 일회성 수정인지 앞으로의 규칙인지 구분한다. 광고 해제를 이미 실행했다는 사실이 있다면 따로 보여준다.
- **완료 기준:** 수정 결과와 적용 범위가 명확하며 같은 메일을 다시 확인할 수 있다.

<a id="cls-06"></a>

### CLS-06. 일반 메일을 중요하게 잘못 분류

범위: **초기 핵심 설계**

- **상황·요청:** 중요 목록에 불필요한 자동 안내가 반복된다.
- **사용 흐름:** 사용자가 일반으로 수정하고 필요한 경우 예외 규칙을 만든다.
- **예외·복구:** 중요도 변경으로 다른 업무·수신 설정을 임의 변경하지 않는다.
- **완료 기준:** 알림·중요 보기에서 지정한 범위만 바뀐다.

<a id="cls-07"></a>

### CLS-07. 답장 필요성과 중요도 구분

범위: **초기 핵심 설계**

- **상황·요청:** 중요한 영수증은 읽기만 하면 되고 평범한 문의에는 답장이 필요하다.
- **사용 흐름:** 유형·중요도·다음 행동을 각각 표시한다.
- **예외·복구:** 중요한 메일을 모두 답장 업무로 만들거나 일반 메일의 요청을 무시하지 않는다.
- **완료 기준:** 사용자에게 필요한 행동이 중요도와 별개로 나타난다.

<a id="cls-08"></a>

### CLS-08. 분류를 확정할 근거 부족

범위: **초기 핵심 설계**

- **상황·요청:** 본문이 짧거나 인용문과 현재 요청이 충돌한다.
- **사용 흐름:** 가능한 근거를 확인하고 필요한 경우 재검토한 뒤 확인 필요로 남긴다.
- **예외·복구:** 큰 모델 재검토도 사실을 확보하지 못하면 임의 확정하지 않는다.
- **완료 기준:** 사용자가 원문과 미확정 이유를 보고 수정한다.

## 9. 대화형 규칙·예외·되돌리기

기능 연결: F7, F9, F10 · 주요 화면: S6, S9

<a id="rul-01"></a>

### RUL-01. 선택한 한 통만 중요 표시

범위: **초기 핵심 설계**

- **상황·요청:** 메일을 선택하고 “이 메일 중요해.”라고 말한다.
- **사용 흐름:** 해당 메일을 중요 표시하고 적용 결과를 알려준다.
- **예외·복구:** 같은 발신자의 과거·미래 메일까지 자동 확대하지 않는다.
- **완료 기준:** 한 통의 표시만 바뀐다.

<a id="rul-02"></a>

### RUL-02. 향후 메일에 지속 규칙 적용

범위: **초기 핵심 설계**

- **상황·요청:** “앞으로 A사 견적은 중요하게 해줘.”라고 한다.
- **사용 흐름:** 조건·계정·행동이 명확하면 규칙을 저장하고 이후 새 메일에 적용한다.
- **예외·복구:** 새 메일마다 같은 승인을 반복 요구하지 않는다. 모호한 계정 범위만 확인한다.
- **완료 기준:** 규칙 목록에서 조건과 적용 계정을 확인할 수 있다.

<a id="rul-03"></a>

### RUL-03. 중요 규칙에 예외 추가

범위: **초기 핵심 설계**

- **상황·요청:** “A사는 중요하지만 행사 광고는 일반으로.”라고 한다.
- **사용 흐름:** 기존 기준에 구체적인 예외를 연결하고 적용 예시를 보여준다.
- **예외·복구:** 주문·보안 안내까지 예외에 포함할 근거가 없으면 확대하지 않는다.
- **완료 기준:** 일반 규칙과 예외의 우선순위가 설명 가능하다.

<a id="rul-04"></a>

### RUL-04. 여러 계정에 같은 기준 적용

범위: **초기 핵심 설계**

- **상황·요청:** “연결한 업무용 계정 모두에 이 기준을 적용해줘.”라고 한다.
- **사용 흐름:** 대상 계정 목록을 확인하고 허용된 업무용 계정에만 적용한다.
- **예외·복구:** 이후 새로 연결하는 계정 포함 여부는 별도 조건으로 남긴다. 개인 계정으로 범위를 넓히지 않는다.
- **완료 기준:** 계정별 적용 결과와 제외된 계정을 보여준다.

<a id="rul-05"></a>

### RUL-05. 과거 메일까지 재분류

범위: **초기 핵심 설계**

- **상황·요청:** “지난달 A사 메일도 같은 기준으로 정리해줘.”라고 한다.
- **사용 흐름:** 지정 기간·계정의 재분류 진행률과 변경 결과를 표시한다.
- **예외·복구:** 수집·분석 제외 범위를 넘어 조회하지 않는다. 기간 밖 자료는 미처리로 남긴다.
- **완료 기준:** 과거 적용 범위와 향후 규칙이 구분된다.

<a id="rul-06"></a>

### RUL-06. 서로 충돌하는 규칙

범위: **초기 핵심 설계**

- **상황·요청:** ‘A사 중요’와 ‘전체 광고 일반’이 동시에 적용된다.
- **사용 흐름:** 명시한 예외·구체적 범위 등 정한 우선순위를 적용하고 설명한다.
- **예외·복구:** 해결할 수 없는 충돌만 사용자에게 확인한다. 조용히 임의 규칙을 삭제하지 않는다.
- **완료 기준:** 적용된 규칙과 충돌 해결 내역을 확인한다.

<a id="rul-07"></a>

### RUL-07. ‘정리해줘’의 의미가 불분명

범위: **초기 핵심 설계**

- **상황·요청:** “이런 메일 다 정리해줘.”라고만 말한다.
- **사용 흐름:** 분류·보관·수신 해제 중 필요한 동작과 범위를 좁혀 확인한다.
- **예외·복구:** 확인 전에 삭제·차단·마케팅 변경을 실행하지 않는다.
- **완료 기준:** 사용자가 의도한 작업만 실행한다.

<a id="rul-08"></a>

### RUL-08. 규칙 일시 중지·재개

범위: **초기 핵심 설계**

- **상황·요청:** 휴가 기간 동안 특정 중요 규칙을 잠시 끄고 싶다.
- **사용 흐름:** 규칙의 활성 상태를 변경하고 이후 적용 여부를 표시한다.
- **예외·복구:** 중지 전에 바뀐 메일을 자동 원복하지 않는다. 자동 종료 날짜 기능이 미제공이면 수동 재개를 안내한다.
- **완료 기준:** 규칙 상태와 기존 분류의 효과가 구분된다.

<a id="rul-09"></a>

### RUL-09. 규칙 수정·되돌리기

범위: **초기 핵심 설계**

- **상황·요청:** 잘못 설정한 조건을 고치거나 직전 변경을 취소한다.
- **사용 흐름:** 변경 전후 버전과 영향을 보여주고 선택한 범위를 복구한다.
- **예외·복구:** 이후 다른 규칙이나 수동 수정이 있는 메일은 충돌을 확인한다. 외부 수신 해제까지 되돌렸다고 안내하지 않는다.
- **완료 기준:** 실제 복구한 범위와 남은 항목이 표시된다.

<a id="rul-10"></a>

### RUL-10. 재분류 도중 규칙·권한이 바뀜

범위: **초기 핵심 설계**

- **상황·요청:** 오래 걸리는 재분류 중 사용자가 기준을 다시 수정하거나 분석을 끈다.
- **사용 흐름:** 작업에 사용한 버전과 현재 설정을 비교해 중단·재처리한다.
- **예외·복구:** 뒤늦은 결과가 최신 수동 수정이나 제외 설정을 덮어쓰지 않는다.
- **완료 기준:** 완료·중단·재검토 항목을 구분한다.

## 10. 가입·연결 서비스 현황

기능 연결: F7, F8, F11 · 주요 화면: S1, S7, S8

<a id="svc-01"></a>

### SVC-01. 지원 서비스의 실제 상태 연결

범위: **초기 핵심 설계**

- **상황·요청:** 쇼핑몰 등 지원되는 서비스의 수신 설정을 확인하고 싶다.
- **사용 흐름:** 해당 서비스에 필요한 별도 인증을 거쳐 제공되는 상태·항목·확인 시각을 가져온다.
- **예외·복구:** 메일 계정 연결을 해당 서비스의 권한으로 대신하지 않는다. 미제공 정보는 확인 불가로 표시한다.
- **완료 기준:** 실제 연동으로 확인한 범위만 현황에 표시한다.

<a id="svc-02"></a>

### SVC-02. 사용자가 서비스 목록 직접 추가

범위: **초기 핵심 설계**

- **상황·요청:** 메일에 가입 흔적이 없지만 사용하는 서비스를 알고 있다.
- **사용 흐름:** 서비스명·사용 계정·수신 선호를 직접 등록하고 사용자 확인 정보로 표시한다.
- **예외·복구:** 직접 등록한 정보를 서비스 서버가 확인한 현재 상태로 표시하지 않는다.
- **완료 기준:** 분석 범위 밖의 서비스도 출처가 분명한 목록으로 관리한다.

<a id="svc-03"></a>

### SVC-03. 가입 메일은 있지만 이미 탈퇴

범위: **초기 핵심 설계**

- **상황·요청:** 예전 가입 메일을 보고 앱이 서비스 후보를 발견했다.
- **사용 흐름:** 현재 상태 미확인 후보로 제시하고 연동 조회 또는 사용자 확인을 받는다.
- **예외·복구:** 사용자가 탈퇴했다고 하면 확인 출처와 날짜를 기록한다. 가입 메일만으로 현재 회원이라고 단정하지 않는다.
- **완료 기준:** 과거 흔적과 현재 사용 상태가 구분된다.

<a id="svc-04"></a>

### SVC-04. 같은 서비스에 여러 계정 사용

범위: **초기 핵심 설계**

- **상황·요청:** 같은 쇼핑몰에 네이버와 Gmail로 각각 가입했다.
- **사용 흐름:** 서비스 아래에 계정별 연결·구독·수신 항목을 나눠 보여준다.
- **예외·복구:** 비슷한 이름이나 같은 발신자 주소만으로 두 계정을 합치지 않는다.
- **완료 기준:** 한 계정의 변경이 다른 계정으로 확대되지 않는다.

<a id="svc-05"></a>

### SVC-05. 오래된 현황 다시 확인

범위: **초기 핵심 설계**

- **상황·요청:** 한 달 전에 확인한 마케팅 동의 상태를 다시 본다.
- **사용 흐름:** 마지막 확인 시각을 표시하고 지원 경로로 갱신하거나 사용자 재확인을 요청한다.
- **예외·복구:** 조회 실패 시 이전 값을 최신 상태처럼 보여주지 않는다.
- **완료 기준:** 확인된 값과 최신성 한계를 함께 확인한다.

<a id="svc-06"></a>

### SVC-06. 지원하지 않는 서비스 발견

범위: **초기 핵심 설계**

- **상황·요청:** API 연결이 없는 서비스에서 광고가 온다.
- **사용 흐름:** 메일 기반 후보와 공식 설정 안내·수동 확인 경로를 제공한다.
- **예외·복구:** 모든 가입 서비스를 조회하는 범용 API가 있다고 안내하거나 이름만 보고 가짜 연결 완료를 만들지 않는다.
- **완료 기준:** 자동 연동과 직접 관리가 필요한 항목을 구분한다.

<a id="svc-07"></a>

### SVC-07. 조회만 가능하고 설정 변경은 불가

범위: **초기 핵심 설계**

- **상황·요청:** 서비스 상태는 불러왔지만 마케팅 변경 권한은 없다.
- **사용 흐름:** 조회 가능한 값과 직접 변경할 수 없는 항목을 표시한다.
- **예외·복구:** 모델을 재호출해 권한 부족을 해결했다고 하지 않는다. 공식 설정 화면에서 수정하도록 안내한다.
- **완료 기준:** 제공하는 동작의 범위가 실제 커넥터와 일치한다.

<a id="svc-08"></a>

### SVC-08. 외부 서비스의 로그인 연결 해제 요청

범위: **초기 핵심 설계**

- **상황·요청:** “이 쇼핑몰의 Google 로그인 연결을 끊고 싶어.”라고 한다.
- **사용 흐름:** 대상 연결과 효과를 구분하고 검증된 경로가 있으면 처리하거나 공식 관리 화면을 안내한다.
- **예외·복구:** 회원 탈퇴·마케팅 해제·우리 앱의 메일 연결 해제로 대체하지 않는다.
- **완료 기준:** 어떤 연결이 해제됐는지 또는 직접 설정할 부분이 명확하다.

<a id="area-uns"></a>

## 11. 마케팅 수신·구독 해제

기능 연결: F9, F11, F12 · 주요 화면: S6, S8

<a id="uns-01"></a>

### UNS-01. 정확한 대상의 마케팅 해제

범위: **초기 핵심 설계**

- **상황·요청:** “A쇼핑몰에서 네이버로 오는 할인 메일만 꺼줘.”라고 한다.
- **사용 흐름:** 서비스·계정·구독·이메일 채널과 지원 경로가 명확하면 그 지시로 실행하고 결과를 기록한다.
- **예외·복구:** 이미 명확히 지시한 범위를 반복 승인받지 않는다. 미확정 부분만 확인한다.
- **완료 기준:** 주문·보안 안내를 유지하며 요청·처리 확인 상태를 구분한다.

<a id="uns-02"></a>

### UNS-02. 이메일만 끄고 다른 채널 유지

범위: **초기 핵심 설계**

- **상황·요청:** 이메일 광고는 끄되 SMS·앱 푸시는 유지하고 싶다.
- **사용 흐름:** 서비스가 제공하는 채널별 항목을 확인하고 이메일만 변경한다.
- **예외·복구:** 채널을 분리할 수 없다면 통합 해제의 효과를 설명하고 임의 실행하지 않는다.
- **완료 기준:** 실제 변경된 채널과 유지된 채널을 표시한다.

<a id="uns-03"></a>

### UNS-03. 광고·필수 안내가 한 설정에 묶임

범위: **초기 핵심 설계**

- **상황·요청:** 해제 버튼이 결제·배송 알림까지 중단할 가능성이 있다.
- **사용 흐름:** 서비스가 제공하는 설정 범위를 확인하고 분리 가능한 항목만 처리한다.
- **예외·복구:** 사용자가 광고만 끄라고 했는데 전체 알림을 끄지 않는다. 적절한 경로가 없으면 직접 설정 필요로 남긴다.
- **완료 기준:** 유지 요청한 필수 안내가 임의 변경되지 않는다.

<a id="uns-04"></a>

### UNS-04. 여러 구독을 한꺼번에 해제

범위: **초기 핵심 설계**

- **상황·요청:** 선택한 뉴스레터 열 개를 해제해 달라고 한다.
- **사용 흐름:** 항목별 계정·구독을 확인하고 지시된 묶음을 처리한다.
- **예외·복구:** 일부 실패·추가 로그인·미지원이 발생하면 개별 결과를 보여주고 성공한 항목을 다시 실행하지 않는다.
- **완료 기준:** 전체 성공으로 뭉뚱그리지 않고 항목별 상태가 남는다.

<a id="uns-05"></a>

### UNS-05. 해제 대상이 모호함

범위: **초기 핵심 설계**

- **상황·요청:** 같은 서비스 계정이 두 개인데 “여기 광고 끊어줘.”라고 한다.
- **사용 흐름:** 현재 선택으로 확정할 수 없으면 어느 계정·구독인지 확인한다.
- **예외·복구:** 모든 계정이나 같은 발신자의 전체 메일로 확대하지 않는다.
- **완료 기준:** 지정한 대상에만 요청이 연결된다.

<a id="uns-06"></a>

### UNS-06. 메일의 수신 해제 링크 이용

범위: **초기 핵심 설계**

- **상황·요청:** 별도 API가 없지만 메일에 수신 해제 경로가 있다.
- **사용 흐름:** 검증된 표준 정보·공식 경로와 실제 해제 범위를 확인해 처리한다.
- **예외·복구:** 본문 지시나 모델이 만든 URL을 무조건 열어 실행하지 않는다. 경로의 신뢰·범위를 확인할 수 없으면 직접 확인으로 전환한다.
- **완료 기준:** 실제 경로와 결과 근거를 기록한다.

<a id="uns-07"></a>

### UNS-07. 로그인·추가 선택이 필요한 해제

범위: **초기 핵심 설계**

- **상황·요청:** 서비스 설정 화면에서 사용자가 직접 로그인해야 한다.
- **사용 흐름:** 공식 설정 화면과 변경할 항목을 안내하고 직접 설정 필요로 표시한다.
- **예외·복구:** 사용자 대신 인증 절차를 우회하거나 화면을 열었다는 이유로 해제 완료 처리하지 않는다.
- **완료 기준:** 직접 확인 또는 허용된 재조회로 결과를 갱신한다.

<a id="uns-08"></a>

### UNS-08. 해제 요청 후 결과 확인 불가

범위: **초기 핵심 설계**

- **상황·요청:** 외부 요청이 시간 초과되거나 완료 응답이 불명확하다.
- **사용 흐름:** 요청됨·결과 확인 필요 상태로 남기고 가능한 상태 재조회로 확인한다.
- **예외·복구:** 통신 성공만으로 해제 완료라고 하거나 확인 없이 반복 요청하지 않는다.
- **완료 기준:** 성공·실패·미확정 중 실제 상태를 표시한다.

<a id="uns-09"></a>

### UNS-09. 해제했는데 광고가 다시 도착

범위: **초기 핵심 설계**

- **상황·요청:** 처리 이후 비슷한 광고가 또 왔다.
- **사용 흐름:** 발송 시점, 다른 계정·구독·채널 여부와 이전 결과를 확인한다.
- **예외·복구:** 무조건 실패 또는 완전 해제 성공이라고 단정하지 않는다. 필요하면 같은 범위의 추가 조치를 제안한다.
- **완료 기준:** 재도착 이유와 다음 확인 대상이 구분된다.

<a id="uns-10"></a>

### UNS-10. 해제한 구독을 다시 받고 싶음

범위: **초기 핵심 설계**

- **상황·요청:** 사용자가 뉴스레터 해제를 후회한다.
- **사용 흐름:** 해당 서비스의 재구독 경로와 가능한 복구 범위를 안내한다.
- **예외·복구:** 규칙 되돌리기처럼 즉시 원복할 수 있다고 약속하지 않는다. 자동 재구독은 검증된 기능과 명시적 지시가 있을 때만 검토한다.
- **완료 기준:** 실제 재구독 여부 또는 사용자가 할 일을 알 수 있다.

<a id="uns-11"></a>

### UNS-11. 해제 묶음 처리 도중 중단

범위: **초기 핵심 설계**

- **상황·요청:** 열 개 중 일부 처리 후 “그만해.”라고 한다.
- **사용 흐름:** 아직 실행하지 않은 요청을 중단하고 이미 완료·요청된 항목을 구분한다.
- **예외·복구:** 외부에 전송된 요청까지 취소됐다고 안내하지 않는다. 미확정 결과는 계속 상태 확인 대상으로 남긴다.
- **완료 기준:** 중단 범위와 이미 발생한 효과가 명확하다.

<a id="uns-12"></a>

### UNS-12. 광고 분류·차단·해제 중 선택

범위: **초기 핵심 설계**

- **상황·요청:** “광고를 안 보이게만 하고 구독은 유지할래.”라고 한다.
- **사용 흐름:** 우리 앱의 분류·알림 선호만 변경한다. 명시적 차단 요청은 실제 지원 기능과 영향을 따로 안내한다.
- **예외·복구:** 보기 조정을 마케팅 동의 변경으로 바꾸지 않는다. 제공하지 않는 제공사 차단은 성공 처리하지 않는다.
- **완료 기준:** 사용자가 선택한 수준의 효과만 발생한다.

## 12. 할 일 생성·연결·상태 변경

기능 연결: F3, F4, F5 · 주요 화면: S2, S3, S6

<a id="tsk-01"></a>

### TSK-01. 메일 한 통에서 여러 할 일 발견

범위: **초기 핵심 설계**

- **상황·요청:** “견적을 보내고 소개 자료도 수정해 주세요.”라는 메일을 받는다.
- **사용 흐름:** 두 행동을 별도 후보로 제안하고 같은 근거 메일을 연결한다.
- **예외·복구:** 사용자가 하나만 채택하거나 합쳐 관리하도록 수정할 수 있다. 단순 읽기만으로 채택하지 않는다.
- **완료 기준:** 각 할 일의 상태·기한을 독립적으로 관리한다.

<a id="tsk-02"></a>

### TSK-02. 여러 메일을 한 업무에 연결

범위: **초기 핵심 설계**

- **상황·요청:** 최초 견적 요청 뒤 요구사항과 기한 변경 메일이 도착한다.
- **사용 흐름:** 기존 업무와의 관계를 확인해 추가 근거·변경 제안을 붙인다.
- **예외·복구:** 같은 제목의 다른 계약이면 합치지 않고 불확실한 연결을 확인받는다.
- **완료 기준:** 하나의 업무에서 관련 대화와 최신 조건을 볼 수 있다.

<a id="tsk-03"></a>

### TSK-03. 상대방이 해야 할 일을 잘못 제안

범위: **초기 핵심 설계**

- **상황·요청:** “내일까지 자료를 보내드리겠습니다.”라는 상대의 메일을 내가 할 일로 오인했다.
- **사용 흐름:** 사용자가 책임 주체를 수정하고 필요한 경우 답변·자료 대기로 전환한다.
- **예외·복구:** 책임 변경을 발신자에게 새 요청 발송으로 확대하지 않는다.
- **완료 기준:** 내가 할 일과 상대를 기다리는 일이 구분된다.

<a id="tsk-04"></a>

### TSK-04. 기한 없음·모호한 날짜

범위: **초기 핵심 설계**

- **상황·요청:** “가능한 빨리” 또는 기한 없는 요청을 받는다.
- **사용 흐름:** 원문 표현과 마감 미확정을 표시하고 사용자가 관리용 날짜를 정하게 한다.
- **예외·복구:** 관리용 날짜를 상대와 합의한 기한으로 기록하지 않는다. 상대 날짜는 원문 시점·시간대를 확인한다.
- **완료 기준:** 원문 기한과 사용자 지정 날짜의 출처가 구분된다.

<a id="tsk-05"></a>

### TSK-05. 기한 변경 제안 수락·거절

범위: **초기 핵심 설계**

- **상황·요청:** 상대가 금요일 마감을 월요일로 바꿨다.
- **사용 흐름:** 이전·새 기한과 근거를 보여주고 사용자가 변경을 확정한다.
- **예외·복구:** 충돌하는 후속 메일이 있으면 최신 합의를 다시 확인한다. 거절 시 기존 기한을 유지한다.
- **완료 기준:** 승인한 기한과 관련 알림만 갱신된다.

<a id="tsk-06"></a>

### TSK-06. 전화·메신저로 처리한 업무 완료

범위: **초기 핵심 설계**

- **상황·요청:** 메일 밖에서 자료를 전달하거나 통화로 해결했다.
- **사용 흐름:** 사용자가 완료 표시와 필요한 메모를 남긴다.
- **예외·복구:** 이메일 증거가 없다는 이유로 완료를 금지하거나 AI가 오프라인 완료를 먼저 단정하지 않는다.
- **완료 기준:** 사용자 확인에 따라 완료 이력이 남는다.

<a id="tsk-07"></a>

### TSK-07. 업무 후보 제외·복원

범위: **초기 핵심 설계**

- **상황·요청:** 광고 문구를 업무로 잘못 제안했다.
- **사용 흐름:** 사용자가 업무 아님·취소·중복 이유로 제외하고 필요하면 복원한다.
- **예외·복구:** 제외를 원문 삭제나 발신자 차단으로 처리하지 않는다.
- **완료 기준:** 제외된 이유와 복원 후 상태를 확인한다.

<a id="tsk-08"></a>

### TSK-08. 여러 요청 중 일부만 완료

범위: **초기 핵심 설계**

- **상황·요청:** 견적은 보냈지만 소개 자료 수정은 끝나지 않았다.
- **사용 흐름:** 완료한 업무만 종료하고 나머지 업무는 진행으로 유지한다.
- **예외·복구:** 한 통의 답장 발송을 연결된 모든 업무의 완료로 해석하지 않는다.
- **완료 기준:** 남은 행동이 오늘·업무 목록에 계속 나타난다.

<a id="tsk-09"></a>

### TSK-09. 완료 후 추가 요청 발생

범위: **초기 핵심 설계**

- **상황·요청:** 완료한 견적에 새로운 수정 요청이 왔다.
- **사용 흐름:** 기존 업무 재개 또는 새 업무 생성의 근거를 제안한다.
- **예외·복구:** 내용이 다른 새 요청을 기존 완료 업무에 조용히 덮어쓰지 않는다.
- **완료 기준:** 사용자가 추가 요청의 관리 방식을 정하고 기존 이력을 보존한다.

<a id="tsk-10"></a>

### TSK-10. 원문 없는 독립 업무 추가

범위: **운영·화면 설계 제안**

- **상황·요청:** 메일 관련 준비 작업을 직접 할 일로 남기고 싶다.
- **사용 흐름:** 직접 추가 기능을 제공한다면 제목·기한·출처를 사용자 입력으로 저장하고 나중에 메일을 연결한다.
- **예외·복구:** 원문이 없는데 AI가 메일 근거를 만들어 붙이지 않는다. 직접 생성 UI의 초기 제공 여부는 미확정이다.
- **완료 기준:** 사용자 입력 업무임이 명확하다.

<a id="tsk-11"></a>

### TSK-11. 업무를 잘못 합치거나 나눔

범위: **초기 핵심 설계**

- **상황·요청:** 서로 다른 거래가 하나로 합쳐졌거나 같은 일이 중복 제안됐다.
- **사용 흐름:** 사용자가 연결을 수정하고 필요하면 업무를 합치거나 나누는 복구 흐름을 제공한다.
- **예외·복구:** 기한·완료 상태가 다르면 충돌 항목을 확인한다. 병합·분리 UI 세부는 설계 대상이다.
- **완료 기준:** 원문 관계와 남은 행동이 사용자가 확인한 구조로 정리된다.

<a id="tsk-12"></a>

### TSK-12. 메일 읽음·보관·발송 후 업무 유지

범위: **초기 핵심 설계**

- **상황·요청:** “내일 보내겠습니다.”라고 회신하고 메일을 읽음 처리했다.
- **사용 흐름:** 회신 사실을 기록하되 실제 자료 전달 업무는 남겨 둔다.
- **예외·복구:** 읽음·보관·발송을 완료의 자동 근거로 삼지 않는다.
- **완료 기준:** 회신 완료와 약속 이행이 별도 상태로 보인다.

## 13. 답변 대기·오늘 화면·리마인더

기능 연결: F4, F5 · 주요 화면: S2, S3, S7

<a id="wai-01"></a>

### WAI-01. 보낸 요청을 답변 대기로 관리

범위: **초기 핵심 설계**

- **사용 흐름:** 기다리는 상대·질문·관련 메일·다시 확인할 날짜를 확인해 등록한다.
- **예외·복구:** 모든 보낸 메일을 자동으로 답변 대기로 만들지 않는다.
- **완료 기준:** 무엇을 누구에게 기다리는지 알 수 있다.

<a id="wai-02"></a>

### WAI-02. 자동 응답·부재중·반송 도착

범위: **초기 핵심 설계**

- **상황·요청:** 부재중 안내나 수신 실패 메시지가 왔다.
- **사용 흐름:** 실제 답변과 구분하고 대기 유지 또는 재연락 필요를 제안한다.
- **예외·복구:** 메시지가 도착했다는 이유로 업무를 완료하지 않는다.
- **완료 기준:** 대기 상태와 전달 문제를 분리해 표시한다.

<a id="wai-03"></a>

### WAI-03. 질문 일부에만 답변

범위: **초기 핵심 설계**

- **상황·요청:** 가격은 받았지만 납기 답변은 없다.
- **사용 흐름:** 받은 답과 남은 질문을 구분해 남은 항목의 대기를 유지하도록 제안한다.
- **예외·복구:** “확인했습니다” 같은 짧은 답을 전체 해결로 해석하지 않는다.
- **완료 기준:** 빠진 질문이 업무 상세와 후속 초안에 남는다.

<a id="wai-04"></a>

### WAI-04. 실질적인 답변·자료 도착

범위: **초기 핵심 설계**

- **상황·요청:** 기다리던 자료가 첨부되어 도착했다.
- **사용 흐름:** 관련 업무에 새 답변을 연결하고 확인·완료 또는 다음 작업을 제안한다.
- **예외·복구:** 사용자 확인 전에 무조건 완료하거나 오래된 대기 알림을 그대로 보내지 않는다.
- **완료 기준:** 답변 수신과 업무 종료 여부를 따로 확인한다.

<a id="wai-05"></a>

### WAI-05. 상대 마감과 내 확인 날짜 구분

범위: **초기 핵심 설계**

- **상황·요청:** 상대는 금요일까지 답하기로 했고 사용자는 목요일에 다시 보고 싶다.
- **사용 흐름:** 상대 약속 기한과 사용자 리마인더 날짜를 각각 저장한다.
- **예외·복구:** 리마인더를 바꿨다는 이유로 상대 약속 날짜를 수정하지 않는다.
- **완료 기준:** 두 날짜의 의미가 화면에서 구분된다.

<a id="wai-06"></a>

### WAI-06. 오늘·기한 지난 일 확인

범위: **초기 핵심 설계**

- **상황·요청:** 하루 업무를 시작하며 “오늘 뭐부터 해야 해?”라고 한다.
- **사용 흐름:** 확정된 기한·중요 기준·답변 대기와 확인 필요 항목을 근거와 함께 정리한다.
- **예외·복구:** 계정이 끊겼거나 분석 중이면 그 한계를 표시한다. 임의의 우선순위를 확정 사실처럼 안내하지 않는다.
- **완료 기준:** 사용자가 근거를 보고 작업 순서를 정한다.

<a id="wai-07"></a>

### WAI-07. 나중에 다시 알림·알림 선호 변경

범위: **초기 핵심 설계**

- **상황·요청:** 지금 처리하기 어려워 내일 다시 확인하고 싶다.
- **사용 흐름:** 재알림 시점을 바꾸고 해당 업무의 상태·원래 기한을 유지한다.
- **예외·복구:** 알림만 미뤘는데 마감까지 연장되었다고 안내하지 않는다. 알림 세부 설정은 실제 제공 범위만 노출한다.
- **완료 기준:** 알림 시점과 업무 기한이 독립적으로 관리된다.

<a id="wai-08"></a>

### WAI-08. 브라우저를 닫거나 알림 권한 거절

범위: **초기 핵심 설계**

- **상황·요청:** 웹사이트를 닫았거나 브라우저 알림을 허용하지 않았다.
- **사용 흐름:** 확정된 서버 리마인더를 관리하고 다시 접속한 오늘 화면에 남긴다.
- **예외·복구:** 브라우저 알림의 전달을 보장하지 않는다. 권한 없이 다른 채널로 자동 발송하지 않는다.
- **완료 기준:** 사용자는 앱 안에서 누락 없이 알림 상태를 확인한다.

<a id="wai-09"></a>

### WAI-09. 이미 처리한 일의 오래된 알림

범위: **초기 핵심 설계**

- **상황·요청:** 다른 기기에서 완료한 뒤 늦게 알림을 눌렀다.
- **사용 흐름:** 최신 업무 상태를 읽고 완료·변경 사실을 표시한다.
- **예외·복구:** 오래된 버튼으로 업무를 재개하거나 중복 발송하지 않는다.
- **완료 기준:** 최신 상태에서 필요한 행동만 제공한다.

### DRF-01. 선택한 대화로 답장 초안
